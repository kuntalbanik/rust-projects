01PyObject — মেমোরিতে একটা Python ভ্যালু দেখতে কেমন

ধরুন Python-এ লিখলেন: x = 42

বামে: একটা raw int, শুধু র ভ্যালু। ডানে: একই ভ্যালুর Python অবজেক্ট — সাথে হেডার জোড়া লাগানো।
ছবিটা যা দেখাচ্ছে

যেকোনো Python ভ্যালু আসলে মেমোরিতে একটা নির্দিষ্ট প্যাটার্নের বক্স — শুরুতে দুটো ফিক্সড ফিল্ড (ob_refcnt, ob_type), তারপর আসল ডেটা। "42" সংখ্যাটা নিজে মাত্র কয়েক বাইট, কিন্তু তাকে বহন করতে হচ্ছে একটা পুরো হেডার — এই হেডারের জন্যই sys.getsizeof(42) "28" রিটার্ন করে, "4" না।

এই হেডারটা প্রতিটা Python ভ্যালুর সাথেই থাকে — একটা string, একটা list-এর প্রতিটা এলিমেন্ট, সবকিছু। এক কোটি সংখ্যার একটা Python list মানে এক কোটিটা আলাদা এই ধরনের বক্স, মেমোরির বিভিন্ন জায়গায় ছড়িয়ে (কারণ list-টা আসলে এই বক্সগুলোর ঠিকানার একটা অ্যারে ধরে রাখে, ভ্যালু নিজে না)।

প্রফেশনাল নোট: এই ছবিটাই ব্যাখ্যা করে কেন NumPy/Rust extension দ্রুত — তারা এই হেডার পুরোপুরি এড়িয়ে যায়, ৭ নং টপিকে সেই ছবি দেখবেন।

02Reference Counting — লাইভ দেখা

a = [1,2,3]; b = a; c = a — তিনজন একই লিস্টকে ধরে আছে

তিনটা ভ্যারিয়েবল, একটাই আসল অবজেক্ট — শুধু refcnt বাড়ে, ডেটা কপি হয় না।
ছবিটা যা দেখাচ্ছে

b = a লেখার মানে এই না যে [1,2,3] আবার নতুন করে তৈরি হলো — শুধু b নামের একটা নতুন "তীর" (রেফারেন্স) একই বক্সের দিকে যোগ হলো, আর সেই বক্সের ভেতরের ob_refcnt সংখ্যাটা ১ বেড়ে গেল। যতক্ষণ কমপক্ষে একটা তীর বক্সটার দিকে আছে, বক্সটা বেঁচে থাকবে। শেষ তীরটা সরে গেলে (refcnt শূন্যে নামলে) — ঠিক তখনই, সাথে সাথে মেমোরি ফ্রি হয়ে যায়।

প্রফেশনাল নোট: PyO3-র Py<T> ঠিক এই তীরগুলোর একটা — Rust-এর Drop ট্রেইট স্বয়ংক্রিয়ভাবে তীরটা সরিয়ে refcnt কমায়, আপনাকে ম্যানুয়াল হিসাব রাখতে হয় না।

03The GIL — একটা তালা, একাধিক থ্রেড

৩টা Python থ্রেড আছে, কিন্তু bytecode চালানোর অনুমতি একবারে একজনেরই

Thread A এখন GIL ধরে আছে, B ও C অপেক্ষা করছে — পালা করে চলবে, একসাথে না।
ছবিটা যা দেখাচ্ছে

একটা মুহূর্তে শুধু একটা থ্রেডের কাছেই "চালানোর অনুমতি" থাকে (solid লাইন = GIL ধরে আছে)। বাকি থ্রেডগুলো ইন্টারপ্রেটার-লেভেলে অপেক্ষা করে (dashed লাইন)। Thread A একটা নির্দিষ্ট সময় পর (বা কোনো I/O করলে) GIL ছেড়ে দেয়, তখন B বা C সুযোগ পায়। এই পালাবদল এত দ্রুত ঘটে যে মনে হয় সমান্তরাল চলছে — কিন্তু CPU-heavy কাজে বাস্তবে এটা সিরিয়াল।

py.allow_threads() কল করার মানে — Rust কোড GIL-এর বৃত্তটা থেকে সাময়িকভাবে বেরিয়ে যাচ্ছে, তখন Thread B/C-ও একই সাথে সত্যিকারের প্যারালালে চলতে পারে (আলাদা CPU কোরে), যতক্ষণ না Rust কোড আবার Python-কে ছুঁতে চায়।

প্রফেশনাল নোট: এই একটা ছবি দিয়েই বোঝা যায় কেন allow_threads-এর ভেতরে কোনো Python অবজেক্ট ছোঁয়া যায় না — GIL ছাড়া থাকলে এই "তালা" প্রোটেকশন নেই, দুটো থ্রেড একই ob_refcnt একসাথে বদলাতে গেলে ডেটা-রেস হয়ে যাবে।

04Rust Ownership & Move — Stack বনাম Heap

let s1 = String::from("hi"); let s2 = s1;

Heap-এর ডেটা এক বিন্দুও নড়েনি — শুধু "মালিকানা" স্ট্যাক থেকে স্ট্যাকে হাত বদল হলো।
ছবিটা যা দেখাচ্ছে

একটা String-এর আসল টেক্সট heap-এ থাকে; স্ট্যাকে থাকে শুধু একটা ছোট "হ্যান্ডেল" (pointer + length + capacity, মাত্র ২৪ বাইট)। s2 = s1 লেখার মানে এই হ্যান্ডেলটা কপি হলো (সস্তা, স্ট্যাক-অপারেশন), কিন্তু heap-এর আসল টেক্সট একবারও কপি হলো না। এরপর s1-কে কম্পাইলার "মৃত" ধরে নেয় (ছবিতে ফিকে/কাটা) — কারণ এখন দুটো হ্যান্ডেল একই heap ডেটার মালিক দাবি করলে, স্কোপ শেষে দুইবার ফ্রি করার চেষ্টা হতো (double-free) — এটাই কম্পাইলার আগেই আটকে দেয়।

প্রফেশনাল নোট: এই ছবিটাই C-তে সবচেয়ে ক্লাসিক বাগের (double-free, dangling pointer) মূল কারণ ব্যাখ্যা করে — C-তে s1-কে "মৃত" ঘোষণা করার কোনো কম্পাইল-টাইম মেকানিজম নেই, তাই দুটো হ্যান্ডেলই বেঁচে থাকে, একটাই ডেটার উপর দুইবার free() কল হওয়ার সুযোগ থেকে যায়।

05Bound<'py, T> — GIL-সেশনের "বেড়া"

একটা Python রেফারেন্স GIL সেশনের বাইরে পালাতে পারে না — কম্পাইল-টাইমেই আটকানো

ড্যাশড বক্সটাই GIL-attach থাকার সময়টুকু — এর ভেতরের সবকিছু বৈধ, বাইরে বের করার চেষ্টা কম্পাইলার আটকে দেয়।
ছবিটা যা দেখাচ্ছে

'py lifetime-টা আক্ষরিক অর্থেই "GIL attach করা আছে" এই সময়সীমাটা প্রতিনিধিত্ব করে (0x00-এর ড্যাশড বক্স)। Bound<'py, PyList> একটা রেফারেন্স যেটা এই বক্সের ভেতরে "বাঁধা" — কম্পাইলার এই রেফারেন্সকে বক্সের বাইরে (যেমন একটা global variable-এ, বা অন্য থ্রেডে) নিয়ে যাওয়ার চেষ্টা দেখলেই এরর দেবে, কারণ বক্সের বাইরে GIL নাও থাকতে পারে, তখন এই রেফারেন্স আর নিরাপদ না।

প্রফেশনাল নোট: এটাই কারণ কেন PyO3-র পুরনো API (&PyAny, কোনো 'py lifetime ছাড়া) কিছু edge case-এ unsound ছিল — সেই টাইপ কম্পাইলারকে বলছিলই না যে এটা GIL-সেশনের সাথে বাঁধা, তাই ভুল করে সেশনের বাইরে ব্যবহার হওয়া আটকানো যেত না।

06Zero-Copy — Python আর Rust একই বাইট দেখছে

একটা NumPy অ্যারে Rust ফাংশনে পাঠালে কী ঘটে — ডেটা কপি হয় না

Python অবজেক্ট আর Rust স্লাইস — দুজনেই একই মেমোরি ঠিকানার দিকে তাকিয়ে আছে।
ছবিটা যা দেখাচ্ছে

NumPy অ্যারে অবজেক্টের নিজের ভেতরে আসল সংখ্যাগুলো থাকে না — এটা শুধু একটা "হেডার" (shape, dtype, strides) যেটা একটা আলাদা raw মেমোরি ব্লকের দিকে পয়েন্ট করে। যখন এই অ্যারে PyO3 ফাংশনে পাঠানো হয়, PyReadonlyArray1 নতুন কোনো কপি তৈরি করে না — এটা শুধু একই raw মেমোরি ব্লকের ঠিকানা আর দৈর্ঘ্য ধরে রাখে, Rust-এর টাইপ-সিস্টেমে। দুটো ভাষা, দুটো "ভিউ", কিন্তু ফিজিক্যালি একটাই মেমোরি।

প্রফেশনাল নোট: এই ছবিটাই ব্যাখ্যা করে কেন .to_vec() কল করলে স্পিড কমে যায় — সেটা এই ডান পাশের বক্স থেকে একটা সম্পূর্ণ নতুন কপি তৈরি করে, "zero-copy" গ্যারান্টি ভেঙে ফেলে।

07NumPy Strides — একটা 2D গ্রিডকে সরল রেখায় গুটিয়ে রাখা

একটা 3×4 অ্যারে আসলে মেমোরিতে একটা সোজা লাইন, গ্রিড না

"stride" মানে এক ধাপ এগোতে কত বাইট স্কিপ করতে হবে — এই সংখ্যাগুলোই 2D শেপ-এর মায়া তৈরি করে।
ছবিটা যা দেখাচ্ছে

NumPy অ্যারে "সারি আর কলাম"-এর মতো দেখতে হলেও, ফিজিক্যাল মেমোরিতে এটা একটা লম্বা, সোজা লাইন — কোনো "সত্যিকারের" 2D স্ট্রাকচার নেই। array[1, 1]-এ পৌঁছাতে NumPy একটা সহজ সূত্র ব্যবহার করে: শুরুর ঠিকানা (base) থেকে, রো-ইনডেক্স × stride_row, প্লাস কলাম-ইনডেক্স × stride_col — যোগ করলেই ঠিক জায়গাটা পাওয়া যায়। "shape (3, 4)" আর "strides (32, 8)" — এই দুটো নাম্বারের জোড়াই পুরো 2D illusion তৈরি করে, আসল ডেটা কিন্তু একটাই ফ্ল্যাট ব্লক।

প্রফেশনাল নোট: এই সূত্রটা বুঝলেই ৮ নং টপিকের "transpose কপি করে না" ব্যাপারটা সহজে বোঝা যাবে — transpose আসলে শুধু stride_row আর stride_col-এর মান অদলবদল করে দেয়, base ঠিকানা বা আসল বাইট একবিন্দুও নড়ে না।

08Contiguous vs Transposed — একই ডেটা, ভিন্ন পথে হাঁটা

b = a.T — কোনো বাইট কপি হয়নি, শুধু "হাঁটার নিয়ম" বদলেছে

উপরে সোজা রাস্তা (contiguous, দ্রুত), নিচে লাফানো রাস্তা (non-contiguous, cache-miss বেশি)।
ছবিটা যা দেখাচ্ছে

a.T লেখার সাথে সাথেই NumPy একটা নতুন অবজেক্ট বানায় ঠিকই, কিন্তু সেটার ভেতরে আসল সংখ্যাগুলোর একটাও কপি হয় না — শুধু নতুন অবজেক্টের strides ভিন্ন সেট করে দেওয়া হয় (row আর col-এর stride অদলবদল)। ফলে যখন আপনি transpose করা অ্যারেটা রো-বাই-রো পড়েন, CPU-কে মেমোরিতে একটানা এগোনোর বদলে লাফিয়ে লাফিয়ে (উপরের ছবির নিচের ঢেউ-খেলানো লাইন) পড়তে হয় — এতে CPU cache বারবার "মিস" করে, যেটা একই পরিমাণ ডেটার জন্যও অনেক ধীর হতে পারে।

প্রফেশনাল নোট: এই কারণেই .as_slice() (0x06-এর zero-copy) non-contiguous অ্যারেতে কাজ করে না — একটা সোজা "স্লাইস" দিয়ে লাফিয়ে-লাফিয়ে পড়ার প্যাটার্ন প্রকাশ করা সম্ভব না। তাই Rust-এ পাঠানোর আগে Python-সাইডে np.ascontiguousarray() দিয়ে "সোজা রাস্তা"-য় ফিরিয়ে আনতে হয় (এটা তখন একটা প্রকৃত কপি করে)।

09Python List বনাম NumPy Array — স্পিডের আসল রহস্য

দুটোই "৫টা সংখ্যা" ধরে রাখছে, কিন্তু মেমোরিতে সম্পূর্ণ ভিন্নভাবে

বামে: প্রতিটা সংখ্যা তার নিজের হেডারসহ, মেমোরিতে ছড়ানো। ডানে: শুধু কাঁচা সংখ্যা, পাশাপাশি।
ছবিটা যা দেখাচ্ছে — সব কিছুর যোগফল

এই একটা ছবিই এই পুরো ডকুমেন্টের সবগুলো কনসেপ্ট একসাথে দেখায়। Python list-এর প্রতিটা সংখ্যা আসলে একটা সম্পূর্ণ PyObject (টপিক ১) — refcount, type-pointer, ভ্যালু সহ — আর এই বক্সগুলো মেমোরিতে যেখানে-সেখানে ছড়িয়ে থাকতে পারে (heap allocator যেখানে জায়গা পায়)। CPU যখন একটার পর একটা এলিমেন্ট পড়ে, প্রতিবার একটা নতুন, দূরের মেমোরি-ঠিকানায় লাফ দিতে হয় — cache miss।

NumPy অ্যারেতে সংখ্যাগুলো একটাই টানা ব্লকে, পাশাপাশি (টপিক ৭-৮ এর "contiguous")। CPU একবার এই ব্লকের শুরুটা cache-এ আনলেই পরের কয়েকটা এলিমেন্টও প্রায় ফ্রি-তে পেয়ে যায় (cache line-এ একসাথে অনেকগুলো আসে)। মেমোরি খরচও কম (কোনো প্রতি-এলিমেন্ট হেডার নেই), আর PyO3/Rust এই একই raw ব্লকে সরাসরি অ্যাক্সেস পায় (টপিক ৬-এর zero-copy) — কোনো Python-object-ওভারহেড, কোনো কপি ছাড়াই।

প্রফেশনাল নোট: এই একটা তুলনাই ব্যাখ্যা করে দেয় পুরো এই লার্নিং-পাথের "কেন" — Rust extension স্পিড পায় কারণ এটা ডানপাশের ছবির জগতে কাজ করে (raw, packed, contiguous), যেখানে pure Python বাধ্য হয় বামপাশের জগতে থাকতে (প্রতিটা ভ্যালু একটা ভারী অবজেক্ট)।
