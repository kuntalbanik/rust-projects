Stack বনাম Heap — দুটো মেমোরি অঞ্চল

কী ও কেন

একটা রানিং প্রোগ্রামের মেমোরি মূলত দুটো ভাগে বিভক্ত। Stack কাজ করে LIFO (Last-In-First-Out) পদ্ধতিতে — প্রতিটা ফাংশন কল একটা "ফ্রেম" পুশ করে, ফাংশন শেষ হলে সেই ফ্রেম পপ হয়ে যায়। Stack-এ শুধু তারাই থাকতে পারে যাদের সাইজ কম্পাইল-টাইমেই নির্দিষ্ট (একটা i32 সবসময় ৪ বাইট, এটা কখনো বদলাবে না)। Heap হলো একটা বড়, আনস্ট্রাকচার্ড মেমোরি পুল যেখান থেকে রানটাইমে ইচ্ছামতো সাইজের ব্লক চাওয়া যায় (allocate) — কিন্তু heap-এ থাকা ডেটা সরাসরি "নাম" দিয়ে অ্যাক্সেস করা যায় না, একটা পয়েন্টার (মেমোরি অ্যাড্রেস) দিয়ে সেটার কাছে পৌঁছাতে হয়, আর সেই পয়েন্টারটাই stack-এ থাকে।

কেন এই বিভাজন — পারফরম্যান্স যুক্তি

Stack-এ push/pop করা মানে শুধু একটা পয়েন্টার (stack pointer) বাড়ানো/কমানো — এক-দুইটা CPU instruction, তাই এক্সট্রিমলি ফাস্ট। Heap-এ অ্যালোকেট করার জন্য allocator-কে খুঁজে বের করতে হয় কোথায় যথেষ্ট ফাঁকা জায়গা আছে — এটা তুলনামূলক ধীর। এই কারণেই Rust (এবং C/C++) যেখানে সম্ভব stack ব্যবহার করে, আর শুধু যেখানে সাইজ রানটাইমে নির্ধারিত হয় বা ডেটা ফাংশনের বাইরেও বাঁচতে হবে, সেখানে heap ব্যবহার করে।

Stack ফ্রেম pointer রাখে, সেই pointer Heap-এর কোনো অ্যালোকেশনের দিকে নির্দেশ করে।
প্রফেশনাল নোট: "স্ট্যাক ওভারফ্লো" ঘটে যখন খুব গভীর রিকার্সন বা খুব বড় লোকাল ভ্যারিয়েবল স্ট্যাকের ফিক্সড সাইজ (সাধারণত কয়েক MB) ছাড়িয়ে যায় — বড় ডেটা তাই ইচ্ছাকৃতভাবে Box-এ heap-এ রাখা হয় (0x02 দেখুন)।
0x01

Stack-এ থাকা সাধারণ ভ্যালু (Scalars)

কী ও কেন

i32, bool, char, f64 — এই ধরনের টাইপের সাইজ কম্পাইল-টাইমেই ফিক্সড (একটা i32 সবসময় ৪ বাইট)। তাই এগুলো সরাসরি stack ফ্রেমে বসে, কোনো heap অ্যালোকেশন লাগে না। এই টাইপগুলোই Rust-এ Copy ট্রেইট implement করে — মানে অ্যাসাইনমেন্টে এদের move করার দরকার নেই, শুধু বিট-বাই-বিট কপি করাই যথেষ্ট (এত সস্তা যে ownership-tracking-এর জটিলতার দরকার নেই)।

চারটা স্কেলার ভ্যারিয়েবল, চারটাই stack frame-এর সংলগ্ন স্লটে বসানো।
প্রফেশনাল নোট: এই ধরনের টাইপ ফাংশনে পাস করার সময় & দিয়ে borrow না করে সরাসরি ভ্যালু হিসেবে পাস করাই বেশি efficient হতে পারে — একটা i32 কপি করা একটা reference পাস করার চেয়েও সস্তা (দুটোই আসলে কয়েক বাইট কপি, কিন্তু reference এক লেয়ার indirection যোগ করে)।
0x02

Box<T> — সবচেয়ে সহজ Heap অ্যালোকেশন

কী ও কেন

Box<T> হলো Rust-এর সবচেয়ে সরল "স্মার্ট পয়েন্টার" — এটা একটা ভ্যালুকে জোর করে heap-এ রাখে, আর stack-এ শুধু heap-এর সেই ঠিকানার দিকে নির্দেশ করা একটা পয়েন্টার (৮ বাইট, 64-bit সিস্টেমে) রাখে। কী গুরুত্বপূর্ণ: Box ownership-এর নিয়মেই চলে (0x04) — যখন Box ভ্যারিয়েবলটা স্কোপ থেকে বেরিয়ে যায়, তার Drop implementation স্বয়ংক্রিয়ভাবে heap-এর মেমোরিও ফ্রি করে দেয় — ম্যানুয়াল free() লাগে না।

কোথায় ব্যবহার / কেন এটাই

(১) যখন কম্পাইল-টাইমে সাইজ জানা নেই (রিকার্সিভ ডেটা-স্ট্রাকচার যেমন লিংকড লিস্ট)। (২) যখন খুব বড় ডেটা stack-এ না রেখে heap-এ রাখতে চান (stack overflow এড়াতে)। (৩) trait object (Box<dyn Trait>) বানাতে, যেখানে কম্পাইল-টাইমে কনক্রিট টাইপ জানা নেই।

Stack-এ একটা মাত্র পয়েন্টার, Heap-এ আসল ডেটা।
Example 
let b = Box::new(5);       // heap-এ 5 অ্যালোকেট হলো, b তে শুধু ঠিকানা
println!("{}", *b);        // * দিয়ে dereference — heap-এর আসল ভ্যালু পড়া
প্রফেশনাল নোট: Box<T>-এর "cost" হলো একটা এক্সট্রা indirection (pointer follow করা) — সাধারণ ব্যবহারে এটা নগণ্য, কিন্তু hot-loop-এ বারবার dereference করলে cache-miss-এর সম্ভাবনা বাড়ে stack-ভিত্তিক ডেটার তুলনায়।
0x03

String & Vec<T> — তিন-শব্দের ফ্যাট পয়েন্টার

কী ও কেন — এটাই সবচেয়ে গুরুত্বপূর্ণ ডায়াগ্রাম

একটা String বা Vec<T> stack-এ ঠিক তিনটা শব্দ (word) (64-bit সিস্টেমে ৩ × ৮ = ২৪ বাইট) নিয়ে থাকে: (১) ptr — heap-এ আসল ডেটা কোথায় শুরু হয়েছে তার ঠিকানা, (২) len — এই মুহূর্তে কতগুলো এলিমেন্ট আছে, (৩) capacity — heap-এ কতগুলো এলিমেন্টের জন্য জায়গা reserve করা আছে (len ≤ capacity সবসময়)। আসল ডেটা (স্ট্রিং-এর ক্যারেক্টার, বা Vec-এর এলিমেন্ট) heap-এ, একটা continuous ব্লকে থাকে।

capacity কেন len-এর চেয়ে বড় থাকতে পারে: যখন আপনি .push() করেন এবং len == capacity হয়ে যায়, নতুন করে বড় একটা heap ব্লক অ্যালোকেট করে পুরনো ডেটা কপি করে আনতে হয় (ব্যয়বহুল) — তাই Rust প্রায়ই "extra" জায়গা রাখে (সাধারণত ডাবল করে) যাতে বারবার reallocate না করতে হয়।

Stack-এ শুধু (ptr, len, capacity) — এটাই "fat pointer" — heap-এ আসল বাইট।
Example 
let mut s = String::with_capacity(8);
s.push_str("hello");
println!("len={} cap={}", s.len(), s.capacity());   // len=5 cap=8
প্রফেশনাল নোট: আগে থেকে সাইজ আন্দাজ থাকলে Vec::with_capacity(n) বা String::with_capacity(n) ব্যবহার করুন — এতে বারবার reallocate+copy এড়ানো যায়, যেটা বড় লুপে .push() করার সময় একটা বড় পারফরম্যান্স পার্থক্য তৈরি করতে পারে।
0x04

Ownership Move — মেমোরি লেভেলে ঠিক কী ঘটে

কী ও কেন

যখন let s2 = s1; লেখেন, Rust heap ডেটা কপি করে না — শুধু stack-এর তিন-শব্দের triplet (ptr, len, capacity) s1 থেকে s2-তে কপি করে (এটা সস্তা, মাত্র ২৪ বাইট)। Heap-এর "hello" ডেটা একই জায়গায় থেকে যায়, শুধু এখন সেটার নতুন "মালিক" s2। তারপর কম্পাইলার s1-কে invalid হিসেবে চিহ্নিত করে দেয় — এর পরে কোথাও s1 ব্যবহারের চেষ্টা করলে কম্পাইল-এরর। এই ব্যবস্থার কারণেই "double free" বাগ কাঠামোগতভাবে অসম্ভব — যদি s1 আর s2 দুটোই independently drop হতো, একই heap মেমোরি দুইবার free হওয়ার চেষ্টা হতো (এটাই C++-এ একটা ক্লাসিক বাগ, যেখানে কম্পাইলার এটা আটকায় না)।

শুধু মালিকানা (৩টা শব্দ) সরে গেল — heap ডেটা একই জায়গায়, একবারই মালিক আছে সবসময়।
Example 
let s1 = String::from("hi");
let s2 = s1;
// println!("{}", s1); // ❌ error[E0382]: borrow of moved value: `s1`
প্রফেশনাল নোট: এই একই ডায়াগ্রাম ফাংশনে ভ্যালু পাস করার সময়ও প্রযোজ্য — fn take(s: String)-এ একটা String পাস করলে সেটাও একটা move, ফাংশনের ভেতরে ownership চলে যায়; ফাংশন শেষ হলে সেই String সেখানেই drop হয়ে যাবে, caller-এর ভ্যারিয়েবল আর বৈধ থাকবে না।
0x05

Move বনাম Clone — মেমোরিতে পার্থক্য

কী ও কেন

যদি সত্যিই দুটো independent, নিজস্ব heap ডেটাসহ কপি দরকার হয় (মূল ভ্যালুটাও ব্যবহার করতে চান), তাহলে .clone() কল করতে হয়। Move-এর বিপরীতে, Clone একটা সম্পূর্ণ নতুন heap ব্লক অ্যালোকেট করে এবং আসল ডেটা বাইট-বাই-বাইট কপি করে সেখানে বসায় — তারপর দুটো সম্পূর্ণ স্বাধীন, একে অপরের থেকে অচেনা মালিক তৈরি হয়।

Clone = নতুন heap অ্যালোকেশন + বাইট কপি — Move-এর চেয়ে বেশি ব্যয়বহুল, কিন্তু দুটো স্বাধীন কপি পাওয়া যায়।
Example 
let s1 = String::from("hi");
let s2 = s1.clone();   // এখন দুটো আলাদা heap allocation
println!("{} {}", s1, s2);   // দুটোই এখনো বৈধ — s1 invalidate হয়নি
প্রফেশনাল নোট: লুপের ভেতরে অকারণে .clone() ব্যবহার করা ("clone আর borrow-checker এড়ানোর সহজ পথ" হিসেবে) একটা খুবই কমন beginner প্যাটার্ন যা পারফরম্যান্স খারাপ করে দেয় — প্রথমে ভাবুন সত্যিই মালিকানার কপি দরকার কিনা, নাকি শুধু একটা & borrow যথেষ্ট (0x06)।
0x06

Borrowing — মেমোরি লেভেলে & ও &mut

কী ও কেন

একটা reference (&s) মেমোরিতে হলো নিজেই একটা ছোট্ট ভ্যালু — মূল ডেটার stack-লোকেশনের (বা heap-ডেটার) ঠিকানা ধরে রাখা একটা পয়েন্টার, সাধারণত ৮ বাইট। কোনো নতুন heap অ্যালোকেশন হয় না, কোনো ডেটা কপি হয় না — শুধু "আমি এখানে তাকাচ্ছি" এই তথ্যটুকু stack-এ যোগ হয়। &s (immutable) একাধিকবার নেওয়া যায় — সবাই শুধু পড়ছে, কোনো দ্বন্দ্ব নেই। &mut s (mutable) একই সময়ে সর্বোচ্চ একটাই থাকতে পারে — কারণ কেউ যদি লিখছে, অন্য কারো একই সময়ে পড়া/লেখা বিপজ্জনক (0x03 আগের ডকুমেন্টে "aliasing rules" দেখুন)।

Reference মানেই একটা ঠিকানা — heap-এ কোনো নতুন কপি না, শুধু কম্পাইলার XOR নিয়ম মেনে চলছে কিনা চেক করে।
Example 
let mut s = String::from("hi");
let r1 = &s;
let r2 = &s;                 // ✅ একাধিক immutable — ঠিক আছে
println!("{} {}", r1, r2);
let rm = &mut s;            // ✅ r1, r2 এখন আর ব্যবহার হচ্ছে না বলেই এটা বৈধ
rm.push_str("!");
প্রফেশনাল নোট: reference-এর "cost" হলো একটা extra pointer-indirection (dereference করতে হয়) — তবু, বড় ডেটা কপি করার (বা move করে ownership হারানোর) চেয়ে প্রায় সবসময় borrow করাই সস্তা এবং idiomatic — ফাংশন ডিজাইনে ডিফল্ট চয়েস &T।
0x07

Struct Layout — Padding & Alignment

কী ও কেন

CPU নির্দিষ্ট সাইজের ডেটা (৪ বাইট, ৮ বাইট) একটা নির্দিষ্ট বাইট-অ্যাড্রেসের গুণিতক থেকে পড়তে সবচেয়ে দ্রুত কাজ করে — একে বলে alignment। একটা u32 কে ৪-বাইট-অ্যালাইনড অ্যাড্রেসে বসাতে হয় (যেমন 0, 4, 8...), নাহলে CPU-কে দুইবার মেমোরি অ্যাক্সেস করতে হতে পারে (কিছু আর্কিটেকচারে এটা এমনকি crash-ও করাতে পারে)। এই কারণে কম্পাইলার struct-এর ফিল্ডের মাঝে মাঝে অদৃশ্য "padding" বাইট ঢুকিয়ে দেয় যাতে প্রতিটা ফিল্ড তার নিজের alignment মেনে চলে।

Padding = "নষ্ট" বাইট না, বরং CPU দ্রুত মেমোরি অ্যাক্সেসের জন্য প্রয়োজনীয় নিয়ম মানার খরচ।
Example 
use std::mem::size_of;

struct Mixed { a: u8, b: u32, c: u16 }
println!("{}", size_of::());   // 12 — 7 বাইট কাঁচা ডেটা + 5 বাইট padding

// ফিল্ড অর্ডার বদলে দিলে padding কমে যেতে পারে:
struct Packed { b: u32, c: u16, a: u8 }
println!("{}", size_of::());  // 8 — বড় ফিল্ড আগে রাখলে padding কম লাগে
প্রফেশনাল নোট: struct-এ ফিল্ড বড়-থেকে-ছোট সাইজ অনুযায়ী সাজালে (এটাকে "field reordering" বলে) padding কমে, struct-টা ছোট হয় — মেমোরি-ভারী অ্যাপ্লিকেশনে (যেমন লাখ লাখ struct ইনস্ট্যান্স) এটা উল্লেখযোগ্য মেমোরি বাঁচাতে পারে। ম্যানুয়ালি চেক করতে std::mem::size_of::<T>() ব্যবহার করুন।
0x08

Enum Layout — Tag + Payload, এবং Niche Optimization

কী ও কেন

একটা enum মেমোরিতে সাধারণত দুই অংশে থাকে: একটা discriminant/tag (কোন variant এটা, একটা ছোট ইন্টিজার হিসেবে) আর একটা payload region যেটা সবচেয়ে বড় variant-এর সমান সাইজের (কারণ যেকোনো variant-এর ডেটা এখানে বসতে হবে, তাই ছোট variant-এর ক্ষেত্রেও বাকি জায়গা "নষ্ট" যায়, অনেকটা union-এর মতো)।

সাধারণ enum-এ tag + বড় payload; বিশেষ ক্ষেত্রে (niche) কম্পাইলার tag-ই বাদ দিয়ে দিতে পারে।
কেন এটাই গুরুত্বপূর্ণ — Niche Optimization ব্যাখ্যা

একটা রেফারেন্স (&T) কখনো null হতে পারে না — Rust-এর টাইপ সিস্টেম এটা গ্যারান্টি দেয়। তাই Option<&T>-এর ক্ষেত্রে কম্পাইলার একটা চালাকি করে: আলাদা tag বাইট না রেখে, "সব-শূন্য" বিট-প্যাটার্নটাকেই (যেটা একটা বৈধ &T কখনো হতে পারে না) None হিসেবে ব্যবহার করে। ফলে Option<&T>-এর সাইজ ঠিক &T-এর সমান — কোনো এক্সট্রা মেমোরি লাগে না। এই "ফাঁকা" (invalid) বিট-প্যাটার্নকে বলে niche।

Example 
use std::mem::size_of;
println!("{}", size_of::<&i32>());              // 8
println!("{}", size_of::<Option<&i32>>());      // 8 — একই! niche optimization
println!("{}", size_of::<Option<i32>>());       // 8 — এখানে কিন্তু আলাদা tag লাগে (i32 এর কোনো "invalid" ভ্যালু নেই)
প্রফেশনাল নোট: এই অপ্টিমাইজেশন জানার প্র্যাকটিক্যাল সুবিধা: Option<&T>, Option<Box<T>>, Option<NonZeroU32>-এর মতো টাইপ ব্যবহার করলে "nullable pointer" প্যাটার্নের জন্য C-তে যা লাগত (একটা আলাদা bool ফ্ল্যাগ, বা null চেক), তার কোনো এক্সট্রা মেমোরি খরচ ছাড়াই একই কাজ পাওয়া যায় — সেফটিও থাকে, স্পিড/সাইজ পেনাল্টিও নেই।
0x09

Slices &[T] — বিদ্যমান মেমোরির উপর ফ্যাট পয়েন্টার

কী ও কেন

একটা slice (&[T] বা &str) হলো একটা "ভিউ" — একটা বিদ্যমান অ্যারে/Vec/String-এর মাঝখানের একটা অংশের দিকে নির্দেশ করা দুই-শব্দের ফ্যাট পয়েন্টার: (ptr, len)। এটা কোনো নতুন মেমোরি অ্যালোকেট করে না — শুধু আসল ডেটার একটা "জানালা" তৈরি করে।

Slice = বিদ্যমান Vec-এর ভেতরে একটা (ptr, len) উইন্ডো — কোনো নতুন heap allocation নেই।
Example 
let v = vec![10, 20, 30, 40, 50, 60];
let s: &[i32] = &v[1..4];   // [20, 30, 40] — v-এর মাঝেই একটা ভিউ
println!("{:?} len={}", s, s.len());
প্রফেশনাল নোট: যেহেতু slice শুধু একটা ভিউ, তাই যতক্ষণ slice বেঁচে আছে, ততক্ষণ borrow-checker আসল v-কে drop হতে দেবে না (lifetime রুল, আগের ডকুমেন্টের 0x04) — এই গ্যারান্টিই নিশ্চিত করে slice কখনো dangling হয়ে যাবে না। ফাংশন প্যারামিটারে &Vec<T>-এর বদলে &[T] নেওয়া বেশি idiomatic — এতে অ্যারে, Vec, slice সব ধরনের ইনপুট গ্রহণ করা যায়।
Rust Memory Layout — ভিজ্যুয়াল ডিপ-ডাইভ। প্রতিটা ডায়াগ্রাম মেমোরির প্রকৃত বাইট-লেভেল অবস্থা সরলীকৃতভাবে দেখায়।
