লেসন ২Intro to Generics

মূল কথা

একটা function parameter হলো ভবিষ্যতের কোনো ভ্যালুর জন্য একটা নাম/প্লেসহোল্ডার। Generic ঠিক একই আইডিয়া, কিন্তু ভ্যালুর জন্য না — টাইপের জন্য একটা প্লেসহোল্ডার। "Generic" শব্দের মানেই "নির্দিষ্ট না" — এটা একটা future, অনির্দিষ্ট টাইপ, যেটা ফাংশন কল হওয়ার সময় ঠিক হবে।

সমস্যাটা কী ছিল

একটা identity_i32 ফাংশন শুধু i32-এর জন্য কাজ করে; bool-এর জন্য দরকার হলে identity_bool নামে আরেকটা ফাংশন লিখতে হয় — অথচ দুটোর ভেতরের লজিক হুবহু একই! শুধু টাইপ হার্ডকোড করার কারণে duplicate কোড লিখতে হচ্ছে।

Generic দিয়ে একটাই ফাংশন — সব টাইপের জন্য, বারবার একই লজিক না লিখেই।
Monomorphization — কম্পাইলারের ভেতরের জাদু

ফাইনাল এক্সিকিউটেবলে আসলে কোনো "generic" থাকে না! কম্পাইলার আপনার generic ফাংশনের সব ব্যবহার (invocation) দেখে, আর প্রতিটা ভিন্ন টাইপের জন্য নিজে থেকেই আলাদা আলাদা কংক্রিট ফাংশন জেনারেট করে দেয় — ঠিক যেন আপনি নিজে হাতে identity_i32, identity_bool লিখেছেন। এই প্রক্রিয়াটার নাম monomorphization।

Example 
fn identity(value: T) -> T {
    value
}

println!("{}", identity(5));           // T = i32
println!("{}", identity(13.14));       // T = f64
println!("{}", identity(true));         // T = bool
প্রফেশনাল নোট: শুধু T লিখলে Rust ভাববে এটা একটা আসল, নির্দিষ্ট টাইপের নাম (যেমন কোনো struct-এর নাম "T" হতে পারে) — তাই ফাংশন নামের ঠিক পরে <T> লিখে আগে থেকে "ঘোষণা" দিতে হয় যে এটা একটা generic, কোনো কংক্রিট টাইপ না।

লেসন ৩The Turbofish Operator

মূল কথা

সাধারণত Rust নিজে থেকেই আন্দাজ করে নেয় generic T কী টাইপ হবে (আর্গুমেন্ট দেখে)। কিন্তু কখনো কখনো আপনি নিজেই স্পষ্ট করে বলতে চাইবেন — এর জন্য turbofish operator: ::<Type> — দুইটা কোলন তারপর angle bracket-এ টাইপ। মজার নাম, কিন্তু কাজটা সহজ: ডিফল্ট অনুমানকে override করা।

turbofish ছাড়া 5 ডিফল্ট i32 হতো — এবার জোর করে i8 বলে দেওয়া হলো।
Example 
identity::<i8>(5);           // ডিফল্টে i32 হতো, এখন i8
identity::<f32>(13.14);
identity::<&str>("hello");
identity::<bool>(true);
প্রফেশনাল নোট: দৈনন্দিন কোডে turbofish খুব বেশি লাগে না (Rust-এর type inference বেশিরভাগ সময় যথেষ্ট), কিন্তু যখন একাধিক টাইপ ফিট করতে পারে এবং কম্পাইলার confuse হয়ে যায় (যেমন .collect::<Vec<i32>>()), তখন এটাই একমাত্র স্পষ্ট সমাধান।

লেসন ৪Multiple Generics

মূল কথা — একই T দুইবার ব্যবহার

make_tuple<T>(first: T, second: T) — একই generic T দুইটা প্যারামিটারে ব্যবহার করলে একটা constraint তৈরি হয়: দুইটা প্যারামিটারকে একই টাইপ হতে হবে। একটা i32 আর একটা &str একসাথে দেওয়া যাবে না — কম্পাইল-এরর।

একাধিক ভিন্ন generic — T আর U

make_tuple<T, U>(first: T, second: U) — এখন দুইটা আলাদা generic, তাই দুইটা প্যারামিটার ভিন্ন টাইপ হতেও পারে, আবার একই টাইপও হতে পারে (বাধ্যতামূলক না, শুধু সম্ভাবনা খুলে দেওয়া হলো)।

একটাই T = একই টাইপ বাধ্যতামূলক; আলাদা T, U = ভিন্ন টাইপের সুযোগ (বাধ্যতা না)।
Example 
fn make_tuple(first: T, second: U) -> (T, U) {
    (first, second)
}

make_tuple(5, "hello");   // T = i32, U = &str — ভিন্ন টাইপ, ঠিক আছে
make_tuple(true, false); // T = bool, U = bool — একই টাইপও চলবে, বাধ্যতা নেই
প্রফেশনাল নোট: কনভেনশন হিসেবে একটা generic হলে T, দুইটা হলে T, U (ইংরেজি বর্ণমালার পরের অক্ষর) ব্যবহার করা হয় — কিন্তু নাম সম্পূর্ণ ডেভেলপারের ইচ্ছা, কম্পাইলার শুধু নামটা কনসিস্টেন্টলি ব্যবহার হচ্ছে কিনা সেটাই চেক করে।

লেসন ৫Generics in Structs

মূল কথা

Function-এর মতোই struct-এও generic ব্যবহার করা যায়। TreasureChest<T>-এ captain সবসময় String (হার্ডকোড), কিন্তু treasure ফিল্ড generic T — তাই একেক instance-এ একেক ধরনের treasure রাখা যায়, কোনো আলাদা আলাদা struct টাইপ ডিফাইন না করেই।

একটাই struct definition, কিন্তু treasure ফিল্ডের টাইপ প্রতিটা instance-এ ভিন্ন হতে পারে।
Example 
#[derive(Debug)]
struct TreasureChest {
    captain: String,
    treasure: T,
}

let gold_chest = TreasureChest { captain: String::from("Firebeard"), treasure: "Gold" };
let silver_chest = TreasureChest { captain: String::from("Bloodsail"), treasure: String::from("Silver") };
প্রফেশনাল নোট: কম্পাইলার struct instantiate করার সময়ই (initial value assignment দেখে) generic T-এর কংক্রিট টাইপ বের করে নেয় — gold_chest-এর প্রকৃত টাইপ আসলে TreasureChest<&str>, যদিও আপনি সেটা লেখেননি।

লেসন ৬Generics and impl Blocks I

মূল কথা — নির্দিষ্ট টাইপের জন্য মেথড

impl TreasureChest<String>-এর ভেতরে ডিফাইন করা মেথড (যেমন clean_treasure) শুধু সেই instance-গুলোতেই কাজ করবে যাদের T ঠিক String। এটা অনেকটা "তালা-চাবি" সিস্টেমের মতো — শুধু ম্যাচিং টাইপের instance-ই সেই মেথড "আনলক" করতে পারে।

"তালা-চাবি" — শুধু T=String-ওয়ালা instance-এই clean_treasure মেথড আনলক হয়।
Example 
impl TreasureChest<String> {
    fn clean_treasure(&mut self) {
        self.treasure = self.treasure.trim().to_string();
    }
}
// silver_chest.clean_treasure()  ✅ — T=String
// gold_chest.clean_treasure()    ❌ error: method not found — T=&str, mismatch
প্রফেশনাল নোট: এই প্যাটার্ন খুব "granular" (সূক্ষ্ম) — একটা [&str; 2] আর একটা [&str; 3]ও Rust-এর কাছে সম্পূর্ণ ভিন্ন টাইপ, তাই তাদের জন্য আলাদা impl ব্লক লাগবে। এটা শক্তিশালী কিন্তু স্কেলযোগ্য না — প্রতিটা সম্ভাব্য টাইপের জন্য আলাদা ব্লক লিখতে হবে। পরের লেসনেই এর সমাধান আসছে।

লেসন ৭Generics and impl Blocks II

মূল কথা — সব টাইপের জন্য মেথড

যেকোনো T-এর জন্য কাজ করবে এমন মেথড চাইলে impl<T> TreasureChest<T> সিনট্যাক্স লাগে — impl-এর ঠিক পরে <T> লিখে "ঘোষণা" দিতে হয় যে এই T generic, কোনো নির্দিষ্ট struct/enum-এর নাম "T" না। এভাবে ডিফাইন করা মেথড (যেমন capital_captain) সব instance-এই কাজ করবে, T যাই হোক না কেন — কারণ এটা শুধু captain ফিল্ড (যেটা সবসময় String, generic-এর উপর নির্ভরই করে না) নিয়ে কাজ করছে।

impl<T> ... <T> মানে "T যা-ই হোক না কেন" — সবার জন্য একই মেথড উপলব্ধ।
Example 
impl TreasureChest {
    fn capital_captain(&self) -> String {
        self.captain.to_uppercase()
    }
}
gold_chest.capital_captain();      // ✅ "FIREBEARD"
silver_chest.capital_captain();    // ✅ "BLOODSAIL"
special_chest.capital_captain();   // ✅ "BOOTYPLUNDER" — T যাই হোক, কাজ করে
প্রফেশনাল নোট: লেসন ৬ আর ৭-এর পার্থক্যটা মনে রাখার সহজ উপায়: impl TreasureChest<String> মানে "শুধু এই একটা নির্দিষ্ট T-এর জন্য", আর impl<T> TreasureChest<T> মানে "যেকোনো T-এর জন্য"। দুটো একসাথেই ব্যবহার করা যায় — একটা struct-এ কিছু মেথড সবার জন্য, কিছু মেথড শুধু নির্দিষ্ট টাইপের জন্য (লেসন ১০-এর project-এ ঠিক এটাই দেখবেন)।

লেসন ৮Generics in Enums

মূল কথা

Enum-এও generic ব্যবহার করা যায়। Cheesesteak<T>-এর Plain variant-এ কোনো ডেটা নেই, কিন্তু Topping(T) variant একটা generic ভ্যালু ধরে রাখে। প্রতিটা variant-এ T ব্যবহার করা বাধ্যতামূলক না — শুধু যেখানে দরকার সেখানেই।

চমকপ্রদ কেস — Plain variant-এও T লাগে!

Cheesesteak::Plain ব্যবহার করলেও, যদি ভ্যারিয়েবলটা mut হয় (ভবিষ্যতে Topping-এ বদলাতে পারে), Rust এখনই জানতে চায় T কী হবে — কারণ কম্পাইলারকে মেমোরির জন্য এবং ভবিষ্যতের কোড ভ্যালিডেট করার জন্য আগে থেকেই টাইপ জানতে হয়। তাই ম্যানুয়ালি : Cheesesteak<String> অ্যানোটেশন দিতে হয়।

যেখানে T-এর ভ্যালু চোখে দেখা যায় সেখানে অটো-অনুমান; Plain-এর মতো ডেটা-বিহীন variant-এ ম্যানুয়াল অ্যানোটেশন লাগে।
Example 
enum Cheesesteak {
    Plain,
    Topping(T),
}

let mushroom = Cheesesteak::Topping("mushroom");   // T = &str
let onions = Cheesesteak::Topping("onion".to_string()); // T = String
let mut plain: Cheesesteak<String> = Cheesesteak::Plain;   // T ম্যানুয়ালি বলে দিতে হলো
plain = Cheesesteak::Topping("bacon".to_string());          // এখন শুধু String-ই দেওয়া যাবে
প্রফেশনাল নোট: এটাই ব্যাখ্যা করে কেন Option<T> আর Result<T, E> (Rust-এর সবচেয়ে ব্যবহৃত দুটো enum) generic — None variant-এর কোনো ডেটা নেই ঠিক Plain-এর মতোই, কিন্তু Some(T)-এর জন্য টাইপ জানা দরকার।

লেসন ১০Project Solution — Chat System

মূল কথা

DigitalContent enum (AudioFile, VideoFile), ChatMessage<T> struct (content: T, time: String)। এখানে লেসন ৬ আর ৭ দুটো একসাথে প্রয়োগ হচ্ছে — একটা impl ব্লক শুধু T=DigitalContent-এর জন্য (consume_entertainment), আরেকটা impl<T> সবার জন্য (retrieve_time)।

একটা মেথড সবার জন্য (generic impl), আরেকটা মেথড শুধু একটা নির্দিষ্ট instance-এর জন্য (specific impl) — দুটো একসাথে।
Example 
#[derive(Debug)]
enum DigitalContent { AudioFile, VideoFile }

#[derive(Debug)]
struct ChatMessage { content: T, time: String }

impl ChatMessage {          // শুধু T = DigitalContent-এর জন্য
    fn consume_entertainment(&self) {
        println!("Watching the {:?}", self.content);
    }
}

impl ChatMessage {                     // যেকোনো T-এর জন্য
    fn retrieve_time(&self) -> String {
        self.time.clone()
    }
}

let audio = ChatMessage { content: DigitalContent::AudioFile, time: String::from("05") };
audio.consume_entertainment();   // ✅ "Watching the AudioFile"
audio.retrieve_time();           // ✅ সব ChatMessage-এই কাজ করে
প্রফেশনাল নোট: retrieve_time-এ self.time সরাসরি return না করে .clone() করা হয়েছে — কারণ সরাসরি return করলে time ফিল্ডের ownership struct থেকে বাইরে চলে যেত (আগের সেকশনের Ownership নিয়ম)। এখানে সেকশন ০৬-এর ধারণাই আবার কাজে লাগছে।

লেসন ১২Section Review — এক নজরে সব

মূল উপমা

"একটা generic একটা টাইপের জন্য ঠিক তা-ই, যা একটা parameter একটা value-র জন্য" — এটাই এই পুরো সেকশনের সারকথা। Parameter ভবিষ্যতের ভ্যালুর জন্য প্লেসহোল্ডার, generic ভবিষ্যতের টাইপের জন্য প্লেসহোল্ডার।

ধারণাএক লাইনে সংজ্ঞা
Generic (T)টাইপের জন্য একটা প্লেসহোল্ডার — কম্পাইল-টাইমে কংক্রিট টাইপে রূপান্তরিত হয়
Monomorphizationকম্পাইলার প্রতিটা ব্যবহৃত টাইপের জন্য আলাদা আলাদা কংক্রিট ফাংশন/স্ট্রাক্ট জেনারেট করে
Turbofish (::<T>)টাইপ ম্যানুয়ালি স্পষ্ট করে বলার সিনট্যাক্স, অনুমানকে override করে
Multiple generics (T, U)একাধিক আলাদা প্লেসহোল্ডার — ভিন্ন টাইপের সুযোগ দেয়, বাধ্যতা না
Generic Structএকটা ফিল্ডের টাইপ instance-ভেদে ভিন্ন হতে পারে
impl Type<Concrete>মেথড শুধু সেই নির্দিষ্ট কংক্রিট টাইপের instance-এই কাজ করে
impl<T> Type<T>মেথড T যাই হোক, সব instance-এই কাজ করে
Generic Enumএকটা variant-এর associated data-র টাইপ ভবিষ্যতে ঠিক হয়
প্রফেশনাল নোট: Generics-এর আসল শক্তি বোঝা যায় যখন দেখবেন Option<T>, Result<T, E>, Vec<T> — Rust-এর প্রায় পুরো স্ট্যান্ডার্ড লাইব্রেরিই generics দিয়ে লেখা। এই সেকশনের বেসিক (বিশেষ করে impl ব্লকের দুই ধরনের সিনট্যাক্স) ভালোভাবে বসে গেলে, লাইব্রেরির কোড পড়া অনেক সহজ হয়ে যাবে।
Rust Generics কোর্স (সেকশন ১১) — আপলোড করা ভিডিও ট্রান্সক্রিপ্ট অনুযায়ী, সহজ বাংলায়, ছবিসহ।
