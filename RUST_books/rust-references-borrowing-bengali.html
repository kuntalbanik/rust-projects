লেসন ২Immutable and Mutable Reference Parameters

মূল কথা — সমস্যার প্রেক্ষাপট

আগের সেকশনের সমস্যা মনে আছে? একটা String ফাংশনে পাঠালে ownership move হয়ে যেত, তাই বারবার return করে ফেরত আনতে হতো (আগের সেকশনের লেসন ১৮)। এবার সমাধান — ফাংশন প্যারামিটারকে reference বানিয়ে দিলে ownership একদমই move হবে না। একটা ফাংশন প্যারামিটার চার রকম হতে পারে:

চারটা অপশন — মালিকানা নেয় কিনা, আর মডিফাই করতে পারে কিনা, এই দুই প্রশ্নের চার কম্বিনেশন।
Example 
fn show_my_meal(meal: &String) {         // শুধু পড়া — ownership লাগবে না
    println!("Meal steps: {meal}");
}

fn add_flour(meal: &mut String) {         // পড়া + মডিফাই — mutable reference লাগবে
    meal.push_str("add flour, ");
}

let mut current_meal = String::new();   // mut লাগবে, কারণ &mut reference বানাতে হবে
add_flour(&mut current_meal);            // আর কোনো return/reassign লাগছে না!
show_my_meal(¤t_meal);
প্রফেশনাল নোট: Reference-এ মেথড কল করলে (যেমন meal.push_str()) Rust স্বয়ংক্রিয়ভাবে dereference করে দেয় — তাই meal আসলে &mut String হলেও ঠিক String-এর মতোই মেথড কল করা যায়, সিনট্যাক্স একই থাকে।

লেসন ৩Multiple Immutable References

মূল কথা — গাড়ি ধার দেওয়ার উপমা

ধরুন আপনার একটা নীল গাড়ি আছে। আপনি দুই বন্ধুকে গাড়ি ধার দিলেন — দুজনেই প্রতিশ্রুতি দিল গাড়ির কোনো পরিবর্তন করবে না (immutable borrow)। যেহেতু কেউই গাড়ি বদলাবে না, দুজনের প্রত্যাশাই (নীল গাড়ি ফেরত পাওয়া) পূরণ হবে — কোনো সমস্যা নেই। এটাই নিয়ম: একই সময়ে যত খুশি immutable reference থাকতে পারে, কারণ কেউই ডেটা বদলাতে পারে না বলে কোনো ঝুঁকি নেই। একে বলা যায় — "যত খুশি পাঠক (reader), কিন্তু একবারে একজনই লেখক (writer)।"

যত খুশি immutable reference একসাথে থাকতে পারে, কারণ কেউই ডেটা বদলাতে পারে না।
Example 
let car = String::from("Red");
let ref1 = &car;
let ref2 = &car;
println!("{ref1} {ref2} {}", &car);   // ✅ তিনটা immutable reference, সব একসাথে বৈধ
প্রফেশনাল নোট: এটাই "reader-writer" লকিং-এর কনসেপ্টের সাথে মিলে যায়, যা অনেক প্রোগ্রামিং সিস্টেমেই দেখা যায় (যেমন ডাটাবেসেও) — একাধিক reader একসাথে নিরাপদ, কিন্তু writer সবসময় exclusive হতে হয়।

লেসন ৪Mutable Reference Restrictions

মূল কথা

একটা ভ্যালুর জন্য একই সময়ে সর্বোচ্চ একটা mutable reference থাকতে পারে — আর সেটা থাকলে, একই সময়ে আর কোনো reference (mutable বা immutable, কোনোটাই না) থাকতে পারবে না। কারণ: mutable reference-এর ডেটা বদলানোর ক্ষমতা আছে, তাই অন্য কোনো reference যদি একই সময়ে সেই ডেটা নিয়ে কাজ করে, সে ভুল/পুরনো ডেটা পেতে পারে (যেমন এক বন্ধু নীল গাড়ি আশা করছে, আরেক বন্ধু সেটা লাল করে দিচ্ছে)।

চমকপ্রদ ব্যতিক্রম — Lifetime

একটা reference-এর lifetime মানে কোড-এ তার "শেষ ব্যবহারের জায়গা" পর্যন্ত। যদি একটা mutable reference-এর শেষ ব্যবহার একটা নতুন reference তৈরির আগেই শেষ হয়ে যায়, Rust এটাকে "coexist করছে না" ধরে নেয় — আর কম্পাইল হয়ে যায়!

"Coexist" মানে শুধু ডিক্লেয়ার করা না — শেষ ব্যবহারের জায়গা পর্যন্ত সময়সীমা ওভারল্যাপ করছে কিনা, সেটাই আসল প্রশ্ন।
Example 
let mut car = String::from("Red");
let ref1 = &mut car;
println!("{ref1}");         // ref1-এর শেষ ব্যবহার এখানেই
let ref2 = &car;         // ✅ এখন বৈধ — ref1 আর "বেঁচে" নেই
println!("{ref2}");
প্রফেশনাল নোট: এই lifetime-সংক্রান্ত সূক্ষ্মতা নিয়ে দুশ্চিন্তা করার দরকার নেই — কম্পাইলার নিজেই বলে দেবে কোথায় নিয়ম ভাঙছেন। মূল নিয়মটা মনে রাখাই যথেষ্ট: একটা mutable reference-এর সাথে অন্য কোনো reference একই সময়ে "সক্রিয়" থাকতে পারবে না।

লেসন ৫Ownership with Immutable and Mutable References

মূল কথা

Immutable reference Copy trait রাখে — কারণ একাধিক immutable reference থাকা নিরাপদ, তাই b = a লিখলে (দুটোই &String) সম্পূর্ণ কপি হয়, কোনো move হয় না, দুজনেই বৈধ থাকে। কিন্তু mutable reference Copy trait রাখে না — কারণ একই সময়ে দুইটা mutable reference থাকা নিয়ম-বিরুদ্ধ (লেসন ৪)। তাই b = a লিখলে (দুটোই &mut String) ownership move হয়ে যায় — ঠিক যেমন heap String নিজেই move হতো।

Immutable reference-এ Copy trait থাকায় assignment মানে কপি; mutable reference-এ move হয়।
Example 
let coffee = String::from("Mocha");
let a = &coffee;
let b = a;                 // কপি — a এখনো বৈধ
println!("{a} {b}");       // ✅ "Mocha Mocha"
প্রফেশনাল নোট: এই একই "Copy trait আছে কিনা" প্রশ্নটাই বারবার ফিরে আসছে — এবার সেটা প্রয়োগ হচ্ছে reference-এর নিজের টাইপের উপর, আসল ডেটার টাইপের উপর না। মনে রাখবেন: &T সবসময় Copy, কিন্তু &mut T কখনোই Copy না — এটা T আসলে কী টাইপ তার উপর নির্ভর করে না।

লেসন ৬Dangling References

মূল কথা

"Dangle" মানে "ঝুলে থাকা, অনির্ভরযোগ্য"। একটা dangling reference এমন একটা ঠিকানা যেখানকার ডেটা আগেই deallocate (মুছে) হয়ে গেছে — যেমন এমন একটা বাড়ির ঠিকানা দেওয়া যেই বাড়িটাই আর নেই। create_city() ফাংশন একটা local city String বানিয়ে তার reference return করার চেষ্টা করলে — ফাংশন শেষে city owner হিসেবে drop হয়ে যাবে, কিন্তু সেই মুছে-যাওয়া ঠিকানার একটা reference ফেরত পাঠানো হচ্ছে। Rust কম্পাইলার এটা কম্পাইল-টাইমেই আটকে দেয়।

যেই বাড়ির ঠিকানা দেওয়া হচ্ছে, সেই বাড়িই যদি ততক্ষণে ভেঙে ফেলা হয়ে যায় — এটাই dangling reference।
Example — সমস্যা ও সমাধান 
// ❌ কম্পাইল-এরর:
fn create_city() -> &String {
    let city = String::from("New York");
    &city   // city তো এখনই drop হবে, এর ঠিকানা কীভাবে বৈধ থাকবে?
}

// ✅ সমাধান — reference না, আসল String-ই return করুন:
fn create_city() -> String {
    String::from("New York")   // ownership move হয়ে যায়, deallocate হয় না
}
প্রফেশনাল নোট: এই নিয়মটাকে বলা হয় — "referent অবশ্যই reference-এর চেয়ে বেশিদিন বাঁচবে"। Rust compiler-এর এরর মেসেজ নিজেই এই ক্ষেত্রে সমাধান সাজেস্ট করে: "you probably want to return the owned value directly" — অর্থাৎ reference না, সরাসরি owned ভ্যালু return করুন।

লেসন ৭Ownership with Arrays and Tuples

মূল কথা

Array/tuple-এর মতো composite টাইপ নিজেও তাদের ভেতরের এলিমেন্টের "owner"। ইনডেক্স করে একটা এলিমেন্ট বের করলে — এলিমেন্টের টাইপ Copy trait রাখে কিনা তার উপর নির্ভর করে কী হবে। bool-এর মতো Copy-টাইপ হলে সমস্যা নেই — একটা কপি বের হয়ে আসে, array অক্ষত থাকে। কিন্তু String-এর মতো non-Copy টাইপ হলে — ownership move করলে array-টা একটা অদ্ভুত "আংশিক মালিকানা" অবস্থায় পড়ে যেত (একটা এলিমেন্ট আছে, একটা "খালি") — তাই Rust এটা সম্পূর্ণ নিষিদ্ধ করে দিয়েছে।

Copy-টাইপ এলিমেন্ট ইনডেক্স করা নিরাপদ; non-Copy টাইপ এলিমেন্ট সরাসরি বের করা নিষিদ্ধ — clone বা reference লাগবে।
Example 
let languages = [String::from("Rust"), String::from("JavaScript")];
// let first = languages[0];        ❌ error: "cannot move out of index"
let first = languages[0].clone();  // ✅ অপশন ১: সম্পূর্ণ কপি (বেশি মেমোরি)
let first = &languages[0];      // ✅ অপশন ২ (idiomatic): শুধু reference — কোনো ডুপ্লিকেশন নেই

// Tuple-এও একই নিয়ম — শুধু ডট-সিনট্যাক্স দিয়ে অ্যাক্সেস:
let languages = (String::from("Rust"), String::from("JavaScript"));
let first = &languages.0;
প্রফেশনাল নোট: দুটো সমাধানের মধ্যে &languages[0] (reference) সবচেয়ে "idiomatic" (মানে — যেটা বেশিরভাগ প্রোডাকশন Rust কোডে দেখবেন) কারণ এটা কোনো এক্সট্রা heap মেমোরি খরচ করে না, শুধু ঠিকানা ধার করে।

লেসন ৯Project Solution — Road Trip

মূল কথা

একটা রোড ট্রিপ মডেল — start_trip() একটা String তৈরি করে return করে (ownership move)। এরপর visit_philadelphia, visit_new_york, visit_boston — প্রতিটা ফাংশন &mut String নেয় (ownership না নিয়ে, শুধু মডিফাই করার অনুমতি নিয়ে), একের পর এক (sequentially, একসাথে না) কল হয় — তাই লেসন ৪-এর নিয়ম ভাঙে না, কারণ কোনো দুইটা mutable reference কখনো coexist করছে না। শেষে show_itinerary(&trip) শুধু পড়ার জন্য immutable reference নেয়।

একের পর এক mutable borrow — কোনো clone ছাড়াই একই String ধাপে ধাপে বদলানো হচ্ছে।
Example 
fn start_trip() -> String { String::from("The plan is...") }

fn visit_philadelphia(trip: &mut String) { trip.push_str("Philadelphia"); }
fn show_itinerary(trip: &String) { println!("{trip}"); }

let mut trip = start_trip();
visit_philadelphia(&mut trip);
trip.push_str(" and ");
// ... visit_new_york, visit_boston একইভাবে ...
show_itinerary(&trip);   // "The plan is...Philadelphia and New York and Boston."
প্রফেশনাল নোট: এটাই পুরো সেকশনের "punch line" — কোনো .clone() ছাড়াই, কোনো return-reassign ছাড়াই, একটা String একাধিক ফাংশন দিয়ে ধাপে ধাপে বদলানো গেল, শুধু references ব্যবহার করে। এটাই references-এর আসল সৌন্দর্য।

লেসন ১১Section Review — এক নজরে সব

Eiffel Tower উপমা

ভিডিওর নিজের উপমা: Eiffel Tower দেখতে চাওয়া প্রতিটা পর্যটকের জন্য একটা করে পুরো টাওয়ার বানানো অবাস্তব — তার বদলে আমরা সবাইকে শুধু ঠিকানা দিই। কোডেও একই — heap ডেটা কপি করার বদলে শুধু তার ঠিকানা (reference) শেয়ার করাই বুদ্ধিমানের কাজ।
