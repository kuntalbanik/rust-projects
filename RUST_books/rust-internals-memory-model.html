Memory Safety Without a Garbage Collector

Rust-এর সবচেয়ে বড় "ট্রিক" — এবং কেন এটা আসলে কোনো ট্রিক না, বরং একটা কম্পাইল-টাইম প্রুফ সিস্টেম।

তিনটা পথ — মেমোরি ম্যানেজমেন্টের ইতিহাস

মেমোরি ম্যানেজ করার তিনটা মূল দর্শন আছে প্রোগ্রামিং ভাষার ইতিহাসে। (১) Manual (C/C++) — ডেভেলপার নিজে হাতে malloc/free কল করে। সবচেয়ে ফাস্ট, কিন্তু ভুল করলে use-after-free, double-free, memory leak, dangling pointer — এই পুরো ক্যাটাগরির বাগ তৈরি হয়, যেগুলো decades ধরে সফটওয়্যার সিকিউরিটি ভালনারেবিলিটির সবচেয়ে বড় উৎস। (২) Garbage Collected (Python, Java, Go, JavaScript) — রানটাইম নিজেই ট্র্যাক করে কোন মেমোরি আর দরকার নেই, পর্যায়ক্রমে স্ক্যান করে ফ্রি করে দেয়। নিরাপদ, কিন্তু রানটাইম ওভারহেড (CPU সাইকেল খরচ করে ট্র্যাকিং/স্ক্যানিংয়ে) এবং অনির্দিষ্ট "pause" মোমেন্ট তৈরি করতে পারে। (৩) Ownership + Borrowing (Rust) — মেমোরি সেফটির নিয়মগুলো কম্পাইল-টাইমেই একটা স্ট্যাটিক অ্যানালাইসিসের (borrow checker) মাধ্যমে ভেরিফাই করা হয়। প্রোগ্রাম কম্পাইল হওয়ার মানেই সেই নিয়মগুলো মানা হয়েছে — রানটাইমে এর জন্য কোনো অতিরিক্ত চেক বা ট্র্যাকিং লাগে না।

মূল অন্তর্দৃষ্টি (The Core Insight)

প্রায় সব মেমোরি-সেফটি বাগের একটাই মূল কারণ: একই মেমোরিতে একাধিক জায়গা থেকে দ্বন্দ্বপূর্ণ (conflicting) অ্যাক্সেস থাকা — যেমন একটা জায়গা থেকে ডেটা মুছে ফেলার পরও আরেকটা জায়গা থেকে সেটা ব্যবহারের চেষ্টা (use-after-free), অথবা একটা থ্রেড ডেটা লিখছে ঠিক তখনই আরেকটা থ্রেড সেটা পড়ছে (data race)। Rust-এর সমাধান হলো: এমন কিছু নিয়ম তৈরি করা যা কম্পাইলার এনফোর্স করে, যাতে এই ধরনের দ্বন্দ্বপূর্ণ অ্যাক্সেস লেখাই অসম্ভব হয়ে যায় — কোড কম্পাইলই হবে না।

চারটা মূল রুল যা এটা সম্ভব করে

(১) প্রতিটা ভ্যালুর ঠিক একজন owner থাকে (0x01)। (২) owner স্কোপের বাইরে গেলে ভ্যালুটা স্বয়ংক্রিয়ভাবে drop হয়ে যায় — ম্যানুয়াল ফ্রি করার দরকার নেই (0x01)। (৩) একই সময়ে হয় একাধিক immutable reference থাকতে পারে, অথবা ঠিক একটা mutable reference — দুটো একসাথে কখনো না (0x02, 0x03)। (৪) কোনো reference কখনো তার আসল ডেটার চেয়ে বেশিদিন বেঁচে থাকতে পারবে না — এটা lifetime দিয়ে ট্র্যাক করা হয় (0x04)।

কেন এটাকে "Zero-Cost Abstraction" বলা হয়

এই পুরো ভেরিফিকেশন প্রক্রিয়া কম্পাইল-টাইমে ঘটে, রানটাইমে না। মানে একবার কোড কম্পাইল হয়ে গেলে, চূড়ান্ত বাইনারিতে এই সেফটি-চেকিংয়ের জন্য কোনো extra CPU সাইকেল খরচ হয় না — কম্পাইল হওয়া মেশিন-কোড প্রায় C-এর মতোই raw এবং দ্রুত। এটা GC-এর সাথে সবচেয়ে বড় পার্থক্য: GC-ভিত্তিক ভাষায় রানটাইমে সবসময় একটা ব্যাকগ্রাউন্ড প্রসেস চলে যেটা মেমোরি ট্র্যাক করছে; Rust-এ এই কাজটা কম্পাইলার একবার, কম্পাইল-টাইমেই করে দেয়।

Example — কম্পাইলার কীভাবে একটা বাগ আটকায় 
fn main() {
    let v = vec![1, 2, 3];
    let v2 = v;              // মালিকানা v থেকে v2-তে move হয়ে গেল
    println!("{:?}", v);   // ❌ কম্পাইল-এরর: "value borrowed after move"
    // এই একই প্যাটার্ন C++-এ কম্পাইল হয়ে যেত, আর রানটাইমে
    // double-free crash অথবা undefined behavior দিত
}
মডেলস্পিডসেফটিরানটাইম ওভারহেডডেভেলপার বার্ডেন
Manual (C/C++)সর্বোচ্চডেভেলপারের উপর নির্ভরনেইসর্বোচ্চ — প্রতিটা alloc/free নিজে ট্র্যাক
GC (Python/Java/Go)মাঝারিরানটাইম-গ্যারান্টেডআছে (ট্র্যাকিং + স্ক্যান)ন্যূনতম — কিছু ভাবতে হয় না
Ownership (Rust)C-এর কাছাকাছিকম্পাইল-টাইম গ্যারান্টেডনেইমাঝারি — কম্পাইলারের সাথে "কথা বলতে" শিখতে হয়
প্রফেশনাল নোট: "borrow checker-এর সাথে যুদ্ধ" — নতুন Rust ডেভেলপারদের এই অভিজ্ঞতা হবেই, এবং এটা আসলে একটা ভালো লক্ষণ — মানে কম্পাইলার সত্যিই একটা সম্ভাব্য বাগ ধরিয়ে দিচ্ছে যেটা অন্য ভাষায় প্রোডাকশনে গিয়ে ধরা পড়ত। যত বেশি এই এরর মেসেজ পড়বেন, তত দ্রুত "Rust-এর মতো চিন্তা করা" রপ্ত হবে।

Ownership — Scope Rules & Drop Behavior

কী কাজ হয় — মেকানিজম

Rust-এ প্রতিটা ভ্যালুর (একটা String, একটা Vec, যেকোনো হিপ-অ্যালোকেটেড ডেটা) ঠিক একজন owner থাকে — একটা ভ্যারিয়েবল যার সাথে ভ্যালুটা বাঁধা। যখন সেই ভ্যারিয়েবলটা তার স্কোপ (সাধারণত একটা { } ব্লক) থেকে বেরিয়ে যায়, Rust কম্পাইলার স্বয়ংক্রিয়ভাবে সেখানে একটা drop() কল ইনজেক্ট করে দেয় — এটাকেই বলে RAII (Resource Acquisition Is Initialization) প্যাটার্ন, যা C++ থেকে এসেছে কিন্তু Rust-এ এটা কম্পাইলার-এনফোর্সড, শুধু কনভেনশন না।

যখন একটা ভ্যালু একটা ভ্যারিয়েবল থেকে আরেকটাতে অ্যাসাইন হয় (let v2 = v1;), ডিফল্টভাবে এটা একটা move — মালিকানা v1 থেকে v2-তে চলে যায়, আর v1 আর বৈধ থাকে না (কম্পাইলার একে "ব্যবহার করলে এরর" হিসেবে ট্র্যাক করে)। এটা copy না — ডেটা মেমোরিতে যেখানে ছিল সেখানেই থাকে, শুধু "কে এর মালিক" এই তথ্যটা বদলায়। ছোট, স্ট্যাক-ভিত্তিক টাইপ (যেমন i32, bool) Copy ট্রেইট implement করে বলে move-এর বদলে সাইলেন্টলি কপি হয়ে যায় — কারণ কপি করাটা এত সস্তা যে move-semantics-এর জটিলতা এখানে অপ্রয়োজনীয়।

Purpose / কেন এটাই — vs manual free() / GC

এই সিস্টেমের গোটা উদ্দেশ্য হলো "কে এই মেমোরি ফ্রি করার দায়িত্বে" — এই প্রশ্নের উত্তর কম্পাইল-টাইমেই, দ্ব্যর্থহীনভাবে ঠিক করে দেওয়া। C-তে এই প্রশ্নের উত্তর ডেভেলপারকে মনে রাখতে হয় (ভুলে গেলে leak, দুইবার free করলে crash); GC-তে রানটাইম ট্র্যাক করে (কিন্তু কখন ঠিক ফ্রি হবে অনিশ্চিত, আর ট্র্যাকিংয়ের খরচ আছে)। Rust-এ owner স্কোপ ছাড়লেই ডিটারমিনিস্টিকভাবে, ঠিক সেই মুহূর্তেই ফ্রি হয় — ফাইল হ্যান্ডেল, নেটওয়ার্ক কানেকশন, লক-এর মতো রিসোর্স ম্যানেজমেন্টের জন্য এই প্রেডিক্টেবিলিটি অত্যন্ত মূল্যবান।

Example 
struct FileGuard { name: String }

impl Drop for FileGuard {
    fn drop(&mut self) {
        println!("closing {}", self.name);   // স্কোপ শেষে স্বয়ংক্রিয়ভাবে চলবে
    }
}

fn main() {
    {
        let _f = FileGuard { name: String::from("data.txt") };
        println!("working...");
    }   // ← এখানে _f স্কোপ ছাড়ছে → drop() স্বয়ংক্রিয়ভাবে কল হবে → "closing data.txt" প্রিন্ট হবে
    println!("done");
}
প্রফেশনাল নোট:
  • যেকোনো "resource wrapper" টাইপ (ফাইল, লক, ডাটাবেস কানেকশন, PyO3-র Py<T>) নিজের Drop implement করে — এটাই Rust-এ resource-cleanup-এর ইউনিফর্ম প্যাটার্ন, try/finally বা context manager-এর কম্পাইলার-এনফোর্সড ভার্সন ভাবতে পারেন।
  • ম্যানুয়ালি আগেই ফ্রি করতে চাইলে drop(value) ফাংশন কল করুন — এটা স্কোপ শেষ হওয়ার আগেই ownership নিয়ে drop ট্রিগার করে।

Borrowing — Immutable vs Mutable References

কী কাজ হয়

Ownership move করা মানে প্রতিবার ডেটা ব্যবহার করতে চাইলে মালিকানা হস্তান্তর করতে হবে — এটা অব্যবহারিক। Borrowing এর সমাধান দেয়: মালিকানা না নিয়ে শুধু একটা "রেফারেন্স" (ঠিকানা) ধার নেওয়া। &T একটা immutable (shared) reference — শুধু পড়া যায়, একসাথে যত খুশি থাকতে পারে। &mut T একটা mutable (exclusive) reference — লেখাও যায়, কিন্তু একই সময়ে সর্বোচ্চ একটাই থাকতে পারে (দেখুন 0x03)।

Purpose / কোথায় ব্যবহার

একটা ফাংশনে বড় ডেটা (যেমন একটা লম্বা Vec বা String) পাঠাতে চাইলে পুরো ডেটা কপি করার বদলে শুধু একটা reference পাঠানো — এটাই সাধারণ, দৈনন্দিন প্যাটার্ন। প্রায় প্রতিটা Rust ফাংশন সিগনেচারে & বা &mut দেখবেন।

কেন এটাই — vs ownership-transfer বা pointer (C)

C-তে raw পয়েন্টার পাস করা যায়, কিন্তু কম্পাইলার কোনো গ্যারান্টি দেয় না সেই পয়েন্টার এখনো বৈধ কিনা, বা একই সময়ে অন্য কেউ সেটা মডিফাই করছে কিনা। Rust-এর &/&mut কম্পাইল-টাইমেই এই দুটো গ্যারান্টি দেয়: (১) reference বৈধ ডেটার দিকেই পয়েন্ট করছে (lifetime চেক, 0x04), (২) mutable আর immutable access একসাথে ঘটছে না (aliasing রুল, 0x03)।

Example 
fn print_len(s: &String) {          // immutable borrow — শুধু পড়ছে
    println!("len = {}", s.len());
}

fn add_exclaim(s: &mut String) {     // mutable borrow — মডিফাই করবে
    s.push_str("!");
}

fn main() {
    let mut greeting = String::from("hello");
    print_len(&greeting);        // ধার নিলাম, মালিকানা হারালাম না
    add_exclaim(&mut greeting);
    println!("{}", greeting);    // "hello!"
}
প্রফেশনাল নোট: ফাংশন ডিজাইন করার সময় ডিফল্ট চয়েস হওয়া উচিত &T (immutable) — শুধু সত্যিই মডিফাই করার দরকার হলে &mut T নিন। এটা caller-কে সবচেয়ে বেশি নমনীয়তা দেয় এবং কোড পড়ার সময় বোঝা যায় কোন ফাংশন ডেটা বদলাতে পারে, কোনটা পারে না।
0x03

Aliasing Rules — Preventing Data Races at Compile Time

কী কাজ হয় — "XOR mutability" নিয়ম

Rust-এর কেন্দ্রীয় নিয়ম (borrow checker যা এনফোর্স করে তার মূল কথা): যেকোনো একটা ডেটার জন্য, একই সময়ে হয় একাধিক immutable reference (&T) থাকতে পারবে, অথবা ঠিক একটা mutable reference (&mut T) — দুটো একসাথে কখনোই না। একে বলা যায় "shared XOR mutable" — হয় শেয়ার্ড (একাধিক রিডার), অথবা এক্সক্লুসিভ (একজন রাইটার), দুটো একসাথে না।

কেন এই নিয়ম? কারণ এই একটা নিয়মই একসাথে দুই ধরনের বাগ আটকায়: (১) iterator invalidation — একটা লিস্ট iterate করার সময় সেটাই মডিফাই করলে (নতুন এলিমেন্ট যোগ করলে মেমোরি reallocate হয়ে যেতে পারে, পুরনো reference dangling হয়ে যায়) — Rust-এ এটা কম্পাইল-এরর, কারণ iterate করার সময় আপনার কাছে একটা & আছে, সাথে &mut নেওয়ার চেষ্টা কম্পাইলার আটকে দেবে। (২) data race — মাল্টি-থ্রেডেড কনটেক্সটে একই ডেটা একই সময়ে একটা থ্রেড লিখছে আরেকটা পড়ছে — যেহেতু এই নিয়ম single-threaded কোডেও এনফোর্সড, থ্রেডের মধ্যে ডেটা শেয়ার করার সময়ও (Arc/Mutex-এর মাধ্যমে) এই একই গ্যারান্টি বজায় থাকে (দেখুন 0x0B)।

Purpose / কোথায় ব্যবহার

এই রুলটা compiler নিজে থেকেই, প্রতিটা ফাংশনে, প্রতিটা ব্লকে চেক করে — আপনাকে আলাদা করে "লক" বা "গার্ড" লিখতে হয় না single-threaded কোডে। এটাই "compile-time data race prevention"-এর মূল ভিত্তি, যা Rust-এর সবচেয়ে বিখ্যাত সেফটি-গ্যারান্টি।

কেন এটাই — vs C++/Java-র রানটাইম লক

C++/Java-তে ডেটা রেস আটকাতে ডেভেলপারকে মনে রেখে mutex লক নিতে হয় — ভুলে গেলে কম্পাইলার কিছু বলবে না, বাগটা রানটাইমে (প্রায়ই অনিয়মিত, রিপ্রোডিউস করা কঠিন এমন crash হিসেবে) ধরা পড়বে। Rust-এ এই একই ক্লাসের বাগ কম্পাইল-টাইমেই ধরা পড়ে — প্রোগ্রাম কম্পাইল হওয়ার মানেই ডেটা-রেস-মুক্ত (এই নির্দিষ্ট ধরনের রেসের জন্য; deadlock এখনো সম্ভব, সেটা এই সিস্টেম আটকায় না)।

Example — কম্পাইলার কীভাবে এটা আটকায় 
fn main() {
    let mut v = vec![1, 2, 3];
    let first = &v[0];        // immutable borrow শুরু
    v.push(4);              // ❌ কম্পাইল-এরর: cannot borrow `v` as mutable
                              //    because it is also borrowed as immutable
    println!("{}", first);
}
// কারণ: push() reallocate করতে পারে, তখন `first` dangling হয়ে যেত — কম্পাইলার এটা আগেই ধরল
প্রফেশনাল নোট: এই নিয়মটাই সবচেয়ে বেশি "borrow checker-এর সাথে লড়াই"-এর অভিজ্ঞতা দেয়, বিশেষ করে struct-এর ভেতরে একাধিক ফিল্ড আলাদাভাবে borrow করতে গেলে। সমাধান প্রায়ই: ছোট ফাংশনে ভাগ করা, অথবা রানটাইম-চেকড বিকল্প (RefCell, Mutex) ব্যবহার করা যেখানে নিয়মটা কম্পাইল-টাইমের বদলে রানটাইমে চেক হয়।
0x04

Lifetimes — Reference Validity Tracking

কী কাজ হয়

Borrowing নিরাপদ রাখতে আরেকটা প্রশ্নের উত্তর দরকার: একটা reference কি সেই সময়টুকু বৈধ থাকবে যতক্ষণ এটা ব্যবহার হচ্ছে? Lifetime ('a-এর মতো অ্যানোটেশন) হলো কম্পাইলারকে এই তথ্য জানানোর ভাষা — "এই reference-টা অন্তত এই স্কোপ পর্যন্ত বৈধ থাকবে।" এটা কোনো রানটাইম ভ্যালু না, শুধু কম্পাইল-টাইমে বিশ্লেষণের জন্য একটা লেবেল।

বেশিরভাগ ক্ষেত্রে (প্রায় ৯০%) কম্পাইলার নিজে থেকেই lifetime অনুমান করে নেয় — এটাকে বলে lifetime elision। শুধু যেখানে অস্পষ্টতা থাকে (যেমন একটা ফাংশন একাধিক reference নেয় এবং তাদের একটা রিটার্ন করে, কম্পাইলার নিশ্চিত না কোনটার lifetime রিটার্ন-ভ্যালুতে বহন হবে) সেখানে ম্যানুয়াল অ্যানোটেশন লিখতে হয়।

Purpose / কোথায় ব্যবহার

একটা struct যদি নিজের ভেতরে একটা reference রাখে (মালিকানা না নিয়ে), তাহলে সেই struct-কে অবশ্যই বলতে হবে সেই reference কতক্ষণ বৈধ থাকবে — নাহলে struct-টা তার ভেতরের reference-এর চেয়ে বেশিদিন বেঁচে থেকে একটা dangling reference ধরে রাখতে পারত (use-after-free)।

কেন এটাই — vs GC-ভিত্তিক ভাষা

Java/Python-এর মতো ভাষায় এই প্রশ্নটাই ওঠে না — GC নিশ্চিত করে কোনো ভ্যালু ততক্ষণ বেঁচে থাকবে যতক্ষণ কেউ তাকে রেফারেন্স করছে (রানটাইমে ট্র্যাক করে)। Rust-এ যেহেতু কোনো রানটাইম ট্র্যাকিং নেই, এই "কতক্ষণ বৈধ" প্রশ্নের উত্তর কম্পাইল-টাইমেই নিশ্চিত করতে হয় — lifetime সেটাই করে, বিনিময়ে GC-এর রানটাইম খরচ ছাড়াই একই সেফটি পাওয়া যায়।

Example 
struct Highlight<'a> {
    text: &'a str,     // এই struct একটা reference ধরে রাখছে, মালিকানা না নিয়ে
}

fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
// এখানে বলা হচ্ছে: রিটার্ন-ভ্যালুর lifetime, x এবং y দুটোর মধ্যে যেটা ছোট, তার সমান

// এই কোড কম্পাইল হবে না, কারণ h এর ভেতরের reference তার নিজের চেয়ে কম বাঁচে:
// let h;
// { let s = String::from("hi"); h = Highlight { text: &s }; } // ❌ s এখানে drop হয়ে যাচ্ছে
// println!("{}", h.text); // কিন্তু h তখনও বেঁচে — dangling reference, কম্পাইলার আটকাবে
প্রফেশনাল নোট: Lifetime দেখে ভয় পাবেন না — বেশিরভাগ প্রোডাকশন Rust কোডে শুধু 'a-এর মতো একটা সাধারণ লেবেল লাগে, জটিল multi-lifetime সিগনেচার কমই দরকার হয়। PyO3-তে Bound<'py, T>-এর 'py ঠিক এই একই কনসেপ্ট — GIL সেশনের lifetime-এর সাথে reference বেঁধে রাখা।
0x05

Structs — Custom Data Structures & Methods

কী কাজ হয়

struct দিয়ে একাধিক সম্পর্কিত ভ্যালু একটা নামড টাইপে গ্রুপ করা যায় — একে বলা হয় product type (কারণ এর সম্ভাব্য ভ্যালুর সংখ্যা প্রতিটা ফিল্ডের সম্ভাব্য ভ্যালুর গুণফলের সমান)। তিন ধরনের struct আছে: সাধারণ named-field struct, tuple struct (ফিল্ডের নাম নেই, শুধু পজিশন — struct Point(f64, f64);), আর unit struct (কোনো ডেটা নেই, শুধু একটা টাইপ মার্কার — struct Marker;)। impl ব্লকের ভেতরে সেই struct-এর মেথড (&self নেয়) এবং associated function (self নেয় না, যেমন কনস্ট্রাক্টর) ডিফাইন করা হয়।

Purpose / কোথায় ব্যবহার

যেকোনো ডোমেইন মডেলিং-এ — একটা পয়েন্ট, একটা ইউজার, একটা কনফিগারেশন। PyO3-তে #[pyclass] struct-গুলো এখান থেকেই আসে — Python-এ যা একটা ক্লাস, তার Rust-প্রতিরূপ একটা annotated struct।

কেন এটাই — vs class-based OOP (Python/Java)

Rust-এ ক্লাসিক্যাল inheritance নেই — struct শুধু ডেটা ধরে, বিহেভিয়ার আসে আলাদা impl ব্লক আর trait implement করার মাধ্যমে (0x08 দেখুন)। এই বিভাজন (ডেটা বনাম বিহেভিয়ার আলাদা) composition-কে inheritance-এর চেয়ে বেশি প্রাধান্য দেয় — যেটা আধুনিক সফটওয়্যার ডিজাইনে সাধারণত পছন্দনীয় (কম কাপলিং, বেশি নমনীয়তা)।

Example 
struct Rectangle {
    width: f64,
    height: f64,
}

impl Rectangle {
    fn new(width: f64, height: f64) -> Self {   // associated function (কনস্ট্রাক্টর)
        Rectangle { width, height }
    }
    fn area(&self) -> f64 {              // মেথড — &self নিচ্ছে
        self.width * self.height
    }
}

let r = Rectangle::new(3.0, 4.0);
println!("{}", r.area());   // 12.0
প্রফেশনাল নোট: Idiomatic Rust-এ একটা কনস্ট্রাক্টরের নাম কনভেনশন অনুযায়ী new() রাখা হয় — এটা কোনো ভাষার নিয়ম না, কমিউনিটি কনভেনশন, কিন্তু GitHub-এর যেকোনো Rust প্রজেক্টে এই প্যাটার্নই দেখবেন।
0x06

Enums — Algebraic Types & Option Modeling

কী কাজ হয়

enum দিয়ে "এই কয়েকটা সম্ভাবনার মধ্যে যেকোনো একটা" — এই ধরনের টাইপ মডেল করা যায়। একে বলা হয় sum type (struct-এর "product type"-এর বিপরীত — সম্ভাব্য ভ্যালুর সংখ্যা প্রতিটা variant-এর সংখ্যার যোগফল)। Rust-এর enum শুধু C-স্টাইল সংখ্যা-লেবেল না — প্রতিটা variant নিজের সাথে ভিন্ন ধরনের ডেটাও বহন করতে পারে, যেটাকে বলে algebraic data type।

Purpose / কোথায় ব্যবহার — Option<T>

Rust-এর স্ট্যান্ডার্ড লাইব্রেরির সবচেয়ে গুরুত্বপূর্ণ enum হলো Option<T> — Some(value) অথবা None। এটা Rust-এর null-হ্যান্ডলিং সিস্টেম: এখানে কোনো "null" পয়েন্টার নেই যা যেকোনো টাইপে সাইলেন্টলি বসে থাকতে পারে (যেমন Java/C-এর NullPointerException)। যেকোনো ভ্যালু যেটা "না-ও থাকতে পারে" তাকে অবশ্যই Option<T>-এ wrap করতে হবে, আর কম্পাইলার বাধ্য করে আপনাকে দুটো কেসই (Some/None) হ্যান্ডেল করতে।

কেন এটাই — vs null (C/Java) বা None (Python)

Python-এ None যেকোনো ভ্যারিয়েবলে সাইলেন্টলি বসতে পারে, আর .method() কল করলে রানটাইমে AttributeError — এটা ধরা পড়ে শুধু তখনই যখন সেই লাইন এক্সিকিউট হয়, প্রোডাকশনেও হতে পারে। Rust-এ Option<T> থেকে ভেতরের ভ্যালু বের করতে বাধ্যতামূলক একটা explicit চেক (match, .unwrap(), if let) লাগে — "ভুলে None হ্যান্ডেল না করা" এই ক্যাটাগরির বাগ কম্পাইল-টাইমেই আটকে যায়।

Example 
enum Shape {
    Circle { radius: f64 },
    Rectangle { width: f64, height: f64 },
    Point,   // কোনো ডেটা নেই এই variant-এ
}

fn find_user(id: u32) -> Option<String> {
    if id == 1 { Some(String::from("Alice")) } else { None }
}
// find_user(2).unwrap() করলে None-এর উপর প্যানিক করবে — কিন্তু কম্পাইলার
// ভেতরের ভ্যালু বের করার আগে আপনাকে Option-টা "মোকাবিলা" করতে বাধ্য করে
প্রফেশনাল নোট: Enum-কে যতটা সম্ভব "state machine" হিসেবে ব্যবহার করুন — যেমন একটা কানেকশনের অবস্থা enum State { Connecting, Connected(SocketAddr), Disconnected(String) }-এর মতো মডেল করলে, প্রতিটা state-এ ঠিক যে ডেটা প্রাসঙ্গিক সেটাই টাইপ-সিস্টেমে এনফোর্স হয় — ভুল state-এ ভুল ডেটা অ্যাক্সেস করার সম্ভাবনা থাকে না।

Pattern Matching — match & if let

কী কাজ হয়

match একটা ভ্যালুর গঠন অনুযায়ী কোড-পাথ বেছে নেয় এবং একই সাথে ভেতরের ডেটা "destructure" (আলাদা করে বের) করে। এটা switch-statement-এর চেয়ে অনেক শক্তিশালী — এটা enum-এর প্রতিটা variant, struct-এর প্রতিটা ফিল্ড, এমনকি নেস্টেড প্যাটার্ন পর্যন্ত ম্যাচ করতে পারে। সবচেয়ে গুরুত্বপূর্ণ ফিচার: কম্পাইলার exhaustiveness check করে — মানে একটা enum-এর সব variant কভার না করলে কম্পাইল-এরর দেবে। if let হলো match-এর একটা সংক্ষিপ্ত রূপ, যখন শুধু একটা নির্দিষ্ট প্যাটার্নে আগ্রহী, বাকিগুলো ignore করতে চান।

Purpose / কেন এটাই — vs if-else chain বা switch

Exhaustiveness check-টাই আসল সুবিধা: ভবিষ্যতে যদি একটা enum-এ নতুন variant যোগ করেন (যেমন Shape-এ Triangle যোগ করলেন), কম্পাইলার সাথে সাথেই দেখিয়ে দেবে কোথায় কোথায় সেই নতুন কেসটা হ্যান্ডেল করা হয়নি। C/Java-র switch-এ এই গ্যারান্টি নেই — একটা নতুন কেস ভুলে গেলে সাইলেন্টলি রানটাইমে ভুল আচরণ করবে।

Example 
fn describe(s: &Shape) -> String {
    match s {
        Shape::Circle { radius } if *radius > 10.0 => format!("big circle"),
        Shape::Circle { radius } => format!("circle r={}", radius),
        Shape::Rectangle { width, height } => format!("rect {}x{}", width, height),
        Shape::Point => String::from("a point"),
        // একটা variant বাদ দিলে এখানেই কম্পাইল-এরর হতো — "non-exhaustive patterns"
    }
}

// if let — শুধু একটা কেসে আগ্রহী হলে:
if let Some(name) = find_user(1) {
    println!("found: {}", name);
}
প্রফেশনাল নোট: exhaustiveness এড়াতে _ => {}-এর মতো একটা "catch-all" বসানো প্রলুব্ধকর, কিন্তু এতে ভবিষ্যতে নতুন variant যোগ হলে কম্পাইলার আর আপনাকে সতর্ক করবে না। যেখানে সম্ভব, প্রতিটা variant explicitly লিখুন — এটাই এই ফিচারের আসল সুরক্ষা।

Traits — Defining Shared Interface Behaviors

কী কাজ হয়

Trait হলো একগুচ্ছ মেথড সিগনেচারের একটা কন্ট্রাক্ট — "যে টাইপ এই ট্রেইট implement করবে, তার এই মেথডগুলো থাকতেই হবে।" এটা concept হিসেবে Python-এর duck typing বা Java-র interface-এর কাছাকাছি, কিন্তু কম্পাইল-টাইমে ভেরিফাইড। Trait-এ ডিফল্ট মেথড implementation-ও থাকতে পারে, যেটা implementing টাইপ চাইলে override করতে পারে বা যেমন আছে তেমনই রেখে দিতে পারে।

দুই ধরনের ডিসপ্যাচ আছে: static dispatch (impl Trait বা generic bound — কম্পাইল-টাইমেই ঠিক হয়ে যায় কোন কনক্রিট টাইপের মেথড কল হবে, কোনো রানটাইম খরচ নেই) আর dynamic dispatch (dyn Trait — একটা vtable-এর মাধ্যমে রানটাইমে ঠিক হয়, একটু খরচ আছে কিন্তু বিভিন্ন কনক্রিট টাইপ একটা কালেকশনে একসাথে রাখা যায়)।

Purpose / কোথায় ব্যবহার

PyO3-র FromPyObject, IntoPyObject, standard library-র Iterator, Display, Clone — এগুলো সবই trait। যেকোনো "এই টাইপগুলোর একটা কমন ক্ষমতা আছে" — এই সম্পর্ক ট্রেইট দিয়ে প্রকাশ করা হয়।

কেন এটাই — vs class inheritance

Inheritance-এ একটা ক্লাস শুধু একটা প্যারেন্ট থেকে ইনহেরিট করতে পারে (বা Python-এ multiple inheritance-এর জটিলতা), আর behavior আর data একসাথে বাঁধা থাকে। Trait দিয়ে একটা টাইপ একসাথে অনেকগুলো ট্রেইট implement করতে পারে (composition-এর মতো), আর data (struct) আর behavior (trait impl) সম্পূর্ণ আলাদা — এটা বেশি নমনীয়, কম কাপলড ডিজাইন দেয়।

Example 
trait Summable {
    fn total(&self) -> f64;
    fn describe(&self) -> String {         // ডিফল্ট implementation
        format!("total is {}", self.total())
    }
}

struct Cart { items: Vec<f64> }

impl Summable for Cart {
    fn total(&self) -> f64 { self.items.iter().sum() }
    // describe() লিখলাম না — ডিফল্টটাই ব্যবহার হবে
}

fn print_total(item: &impl Summable) {   // static dispatch — জিরো রানটাইম কস্ট
    println!("{}", item.describe());
}
প্রফেশনাল নোট: নতুনদের জন্য সাধারণ পরামর্শ: যতক্ষণ না সত্যিই বিভিন্ন কনক্রিট টাইপ একই কালেকশনে (Vec<Box<dyn Trait>>) রাখার দরকার পড়ছে, ততক্ষণ static dispatch (impl Trait/generics) ব্যবহার করুন — এটা দ্রুত এবং সাধারণত সহজ বোঝা যায়।

Generics — Abstract Types Without Runtime Cost

কী কাজ হয় — Monomorphization

Generics দিয়ে এক কোড একাধিক টাইপে কাজ করে — fn largest<T: PartialOrd>(list: &[T]) -> &T যেকোনো comparable টাইপে চলবে। কিন্তু Java-র generics (type erasure — রানটাইমে সব জেনেরিক টাইপ মুছে Object হয়ে যায়, তাই রানটাইম টাইপ-চেক আর কাস্টিং লাগে) থেকে Rust-এর পদ্ধতি সম্পূর্ণ আলাদা। Rust কম্পাইল-টাইমে monomorphization করে — প্রতিটা কনক্রিট টাইপের জন্য যেটা এই generic ফাংশন কল করা হয়েছে, কম্পাইলার আলাদা আলাদা, স্পেশালাইজড মেশিন-কোড জেনারেট করে দেয় (ঠিক যেন আপনি হাতে প্রতিটা টাইপের জন্য আলাদা ফাংশন লিখেছেন)।

Purpose / কোথায় ব্যবহার

কোড পুনরাবৃত্তি এড়ানো, অথচ কোনো রানটাইম পারফরম্যান্স খরচ ছাড়াই। Vec<T>, Option<T>, HashMap<K, V> — Rust-এর প্রায় পুরো স্ট্যান্ডার্ড লাইব্রেরি generics দিয়ে লেখা।

কেন এটাই — vs Java erasure / Python duck typing

Monomorphization মানে জেনারেট হওয়া মেশিন-কোড ঠিক ততটাই দ্রুত যতটা হাতে-লেখা স্পেশালাইজড কোড হতো — "abstract type নেওয়া"-র জন্য কোনো রানটাইম মূল্য দিতে হয় না (তাই "zero-cost abstraction")। ট্রেড-অফ: প্রতিটা ব্যবহৃত কনক্রিট টাইপের জন্য আলাদা কোড জেনারেট হয় বলে বাইনারি সাইজ কিছুটা বড় হতে পারে (একে "code bloat" বলা হয়) এবং কম্পাইল টাইম বাড়ে — কিন্তু এটা রানটাইম স্পিডের বিনিময়ে একটা সচেতন ট্রেড-অফ।

Example 
fn largest(list: &[T]) -> T {
    let mut max = list[0];
    for &item in list {
        if item > max { max = item; }
    }
    max
}

let nums = vec![3, 7, 2];
let chars = vec!['y', 'm', 'a'];
println!("{}", largest(&nums));    // কম্পাইলার largest:: জেনারেট করল
println!("{}", largest(&chars));   // আলাদাভাবে largest:: জেনারেট করল
প্রফেশনাল নোট: T: PartialOrd + Copy-এর মতো ট্রেইট-বাউন্ড পড়তে শিখুন — এটা বলছে "T যেকোনো টাইপ হতে পারে, যতক্ষণ সেটা তুলনা করা যায় (PartialOrd) এবং কপি করা সস্তা (Copy)।" PyO3 কোডে where T: Send + Sync-এর মতো বাউন্ড এই একই ধারণা।

Result & Option — Explicit Error and Null Handling

কী কাজ হয়

Option<T> (0x06-এ দেখা হয়েছে) "ভ্যালু আছে বা নেই" মডেল করে। Result<T, E> একই কনসেপ্ট এরর-হ্যান্ডলিংয়ে প্রয়োগ করে — Ok(value) অথবা Err(error)। দুটোই enum (0x06), তাই match দিয়ে হ্যান্ডেল করা যায়, কিন্তু দৈনন্দিন ব্যবহারে ? অপারেটর সবচেয়ে গুরুত্বপূর্ণ — একটা ফাংশনের ভেতরে expr? লিখলে, expr যদি Err/None হয়, সেটা সাথে সাথেই পুরো ফাংশন থেকে রিটার্ন হয়ে যায় (caller-এর কাছে propagate); Ok/Some হলে ভেতরের ভ্যালুটা "আনর‍্যাপ" হয়ে এক্সপ্রেশনের ভ্যালু হয়ে যায়।

Purpose / কোথায় ব্যবহার

যেকোনো অপারেশন যা ব্যর্থ হতে পারে (ফাইল পড়া, নেটওয়ার্ক কল, পার্সিং) — সবই Result রিটার্ন করে। PyO3-র PyResult<T> আসলে Result<T, PyErr>-এরই একটা টাইপ-অ্যালিয়াস।

কেন এটাই — vs exceptions (Python/Java)

Exception-ভিত্তিক ভাষায় একটা ফাংশন সিগনেচার দেখে বোঝা যায় না সেটা এরর থ্রো করতে পারে কিনা (checked exception ছাড়া) — এরর-হ্যান্ডলিং "invisible control flow"। Rust-এ Result<T, E> রিটার্ন-টাইপের অংশ — ফাংশন সিগনেচার দেখেই জানা যায় এটা ব্যর্থ হতে পারে কিনা, এবং কম্পাইলার Result ignore করলে ওয়ার্নিং দেয় (#[must_use])। এটা এরর-হ্যান্ডলিংকে "invisible" থেকে "explicit, টাইপ-চেকড" বানিয়ে দেয়।

Example 
use std::num::ParseIntError;

fn parse_and_double(s: &str) -> Result<i32, ParseIntError> {
    let n: i32 = s.parse()?;   // এরর হলে এখানেই রিটার্ন হয়ে যায়, propagate করে
    Ok(n * 2)
}

fn process() -> Result<(), ParseIntError> {
    let result = parse_and_double("21")?;   // আরেকটা লেয়ারে propagate
    println!("{}", result);
    Ok(())
}
প্রফেশনাল নোট: .unwrap() শুধু প্রোটোটাইপ/টেস্টে ব্যবহার করুন — এটা Err/None হলে সরাসরি panic করে। প্রোডাকশন কোডে সবসময় ? বা match/.unwrap_or()/.unwrap_or_else()-এর মতো গ্রেসফুল বিকল্প ব্যবহার করুন।

Fearless Concurrency — Send & Sync

কী কাজ হয়

Send আর Sync হলো দুটো "marker trait" (কোনো মেথড নেই, শুধু কম্পাইলারের জন্য একটা সিগনাল) যা 0x03-এর aliasing রুলকে থ্রেড-বাউন্ডারির ওপারেও প্রসারিত করে। Send: একটা টাইপের মালিকানা এক থ্রেড থেকে আরেক থ্রেডে ট্রান্সফার করা সেফ কিনা। Sync: একটা টাইপের &T (রেফারেন্স) একাধিক থ্রেড থেকে একসাথে অ্যাক্সেস করা সেফ কিনা (একে সমতুল্যভাবে বলা যায়: T Sync হয় যদি &T Send হয়)।

এই দুটো trait প্রায় সবসময় কম্পাইলার নিজে থেকেই auto-derive করে দেয় — যদি একটা struct-এর সব ফিল্ড নিজেরাই Send/Sync হয়, তাহলে সেই struct-ও স্বয়ংক্রিয়ভাবে Send/Sync। শুধু যেসব টাইপ থ্রেড-আনসেফ raw অপারেশন (যেমন Rc, যেটা refcount আপডেট করার সময় লক নেয় না) ব্যবহার করে, তারা ইচ্ছাকৃতভাবে Send/Sync না — কম্পাইলার সেটাও নিজেই বুঝে ফেলে।

Purpose / কোথায় ব্যবহার

যখন আপনি thread::spawn() দিয়ে একটা নতুন থ্রেডে ডেটা পাঠান, কম্পাইলার চেক করে সেই ডেটা Send কিনা — Send না হলে কম্পাইলই হবে না। PyO3-তে GIL রিলিজ করে প্যারালাল কাজ করার সময় (py.allow_threads(), দেখুন পূর্ববর্তী ডকুমেন্টের 6.5) আপনার ডেটা টাইপগুলোকে Send + Sync হতেই হবে।

কেন এটাই — vs C++/Java-র রানটাইম-চেকড থ্রেড-সেফটি

C++/Java-তে থ্রেড-সেফটি নিশ্চিত করা সম্পূর্ণ ডেভেলপারের দায়িত্ব ও ডকুমেন্টেশনের উপর নির্ভর করে — "এই ক্লাসটা thread-safe" এমন একটা কমেন্ট থাকতে পারে, কিন্তু কম্পাইলার এটা ভেরিফাই করে না। Rust-এ Send/Sync একটা টাইপ-সিস্টেম-লেভেল গ্যারান্টি — একটা থ্রেড-আনসেফ টাইপ ভুল করে থ্রেডের মধ্যে শেয়ার করার চেষ্টা করলে প্রোগ্রাম কম্পাইলই হবে না, রানটাইমে ধরা পড়বে না। এই কারণেই এই ফিচারের নাম "fearless concurrency" — নির্ভয়ে মাল্টি-থ্রেডেড কোড লেখা যায়, কারণ কম্পাইলার সবচেয়ে ভয়ংকর ক্লাসের বাগ (ডেটা রেস) আগেই ধরে ফেলবে।

Example 
use std::sync::{Arc, Mutex};
use std::thread;

let counter = Arc::new(Mutex::new(0));   // Arc: multi-owner, Mutex: রানটাইম-চেকড mutable access
let mut handles = vec![];

for _ in 0..5 {
    let c = Arc::clone(&counter);
    handles.push(thread::spawn(move || {
        let mut num = c.lock().unwrap();
        *num += 1;
    }));
}
for h in handles { h.join().unwrap(); }
println!("{}", *counter.lock().unwrap());   // 5 — গ্যারান্টেড, কোনো রেস কন্ডিশন নেই
প্রফেশনাল নোট:
  • Arc (Atomic Rc) — Rc-এর থ্রেড-সেফ ভার্সন, একাধিক থ্রেডের মধ্যে মালিকানা শেয়ার করতে; Mutex — রানটাইমে লক নিয়ে mutable access দেয়, যেখানে কম্পাইল-টাইম aliasing রুল যথেষ্ট না (multi-owner + mutation চাই)।
  • rayon (.par_iter())-এর মতো লাইব্রেরি এই Send/Sync গ্যারান্টির উপরেই দাঁড়িয়ে — এই কারণেই .iter()-কে .par_iter()-এ বদলানো এত নিরাপদ এবং সহজ।

Async/Await — Non-Blocking Tasks & Futures

কী কাজ হয় — মেকানিজম

async fn একটা ফাংশন লেখে যা সরাসরি রেজাল্ট রিটার্ন করে না — এটা একটা Future রিটার্ন করে, যেটা মূলত একটা "স্টেট মেশিন" যা describe করে কাজটা কীভাবে ধাপে ধাপে এগোবে। একটা Future নিজে থেকে কিছুই করে না যতক্ষণ না কেউ এটাকে poll করে — একটা executor (যেমন tokio ক্রেট, যেহেতু std লাইব্রেরিতে কোনো বিল্ট-ইন executor নেই) বারবার Future-টাকে poll করে, আর Future হয় "এখনো রেডি না" (Poll::Pending) বলে, অথবা রেজাল্ট রেডি হলে (Poll::Ready(value)) রিটার্ন করে।

এটা cooperative scheduling — OS থ্রেডের মতো preemptive না (যেখানে OS যেকোনো মুহূর্তে থ্রেড বদলে দিতে পারে), বরং একটা টাস্ক নিজে থেকেই "আমি এখন অপেক্ষা করছি (যেমন নেটওয়ার্ক রেসপন্স)" বলে কন্ট্রোল ছেড়ে দেয়, যাতে executor অন্য কোনো টাস্ক চালাতে পারে। এভাবে একটা মাত্র OS থ্রেডেই হাজার হাজার concurrent টাস্ক চালানো সম্ভব — প্রতিটার জন্য আলাদা OS থ্রেড (যেটা ভারী — কয়েক MB স্ট্যাক প্রতিটার) লাগে না।

Purpose / কোথায় ব্যবহার

I/O-bound কাজ — নেটওয়ার্ক সার্ভার, একসাথে হাজার হাজার HTTP রিকোয়েস্ট হ্যান্ডেল করা, ডাটাবেস কল — এখানে async/await সবচেয়ে কার্যকর, কারণ বেশিরভাগ সময় টাস্ক "অপেক্ষা করছে" (I/O সম্পন্ন হওয়ার), CPU-তে কিছু করছে না।

কেন এটাই — vs OS থ্রেড / Python asyncio

প্রতিটা OS থ্রেড তৈরি করা এবং কনটেক্সট-সুইচ করা তুলনামূলক ভারী (মেমোরি + কার্নেল ওভারহেড) — হাজার হাজার concurrent কানেকশনের জন্য হাজার হাজার OS থ্রেড ব্যবহারিক না। Async টাস্ক অনেক হালকা (শুধু একটা স্টেট মেশিন, স্ট্যাক লাগে না পুরোটা) — একই হার্ডওয়্যারে অনেক বেশি concurrency সম্ভব। Python-এর asyncio-র সাথে কনসেপ্টগতভাবে মিল আছে, কিন্তু Rust-এর async এখনো একটা GIL-এর মতো বাধা ছাড়াই সত্যিকারের মাল্টি-কোর প্যারালালিজমের সাথে মিশতে পারে (executor একাধিক থ্রেডে টাস্ক ছড়িয়ে দিতে পারে)।

Example 
// Cargo.toml: tokio = { version = "1", features = ["full"] }

async fn fetch_data(url: &str) -> String {
    // (সরলীকৃত) নেটওয়ার্ক কল — এই .await পয়েন্টে টাস্ক কন্ট্রোল ছেড়ে দেয়
    reqwest::get(url).await.unwrap().text().await.unwrap()
}

#[tokio::main]
async fn main() {
    let (a, b) = tokio::join!(
        fetch_data("https://example.com/a"),
        fetch_data("https://example.com/b"),
    );   // দুটো রিকোয়েস্ট একসাথে (concurrently) চলবে, সিরিয়ালি না
    println!("{} {}", a.len(), b.len());
}
প্রফেশনাল নোট:
  • PyO3 extension-এ async সাধারণত সরাসরি দরকার হয় না — CPU-bound extension-এর জন্য allow_threads + rayon (0x0B-এর মতো) যথেষ্ট। async মূলত I/O-bound নেটওয়ার্ক/সার্ভার কোডের জন্য।
  • একটা কমন ভুল: async fn-এর ভেতরে CPU-heavy ব্লকিং কাজ করা — এটা পুরো executor-কে থামিয়ে দিতে পারে; ভারী গণনার জন্য tokio::task::spawn_blocking ব্যবহার করুন।

Unsafe Rust — Bypassing Compiler Checks

কী কাজ হয় — পাঁচটা "সুপারপাওয়ার"

unsafe ব্লক কম্পাইলারের normal borrow-checking পুরোপুরি বন্ধ করে দেয় না — এটা শুধু পাঁচটা নির্দিষ্ট অপারেশনের অনুমতি দেয় যা normal Rust-এ নিষিদ্ধ: (১) raw pointer dereference, (২) unsafe ফাংশন/মেথড কল করা (যেমন FFI দিয়ে C ফাংশন কল), (৩) mutable static ভ্যারিয়েবল অ্যাক্সেস করা, (৪) unsafe trait implement করা, (৫) union-এর ফিল্ড অ্যাক্সেস করা। এই পাঁচটা অপারেশনের প্রতিটাই এমন কিছু যেখানে কম্পাইলার নিজে থেকে সেফটি প্রমাণ করতে পারে না — unsafe লিখে ডেভেলপার বলছে "আমি ম্যানুয়ালি যাচাই করেছি এটা সেফ।"

Purpose / কোথায় লাগে

নিচু স্তরের সিস্টেম প্রোগ্রামিং, অন্য ভাষার (C) সাথে FFI, খুব পারফরম্যান্স-ক্রিটিক্যাল কোডে বাউন্ডস-চেকিং এড়ানো, অথবা এমন ডেটা-স্ট্রাকচার (যেমন কিছু বিশেষ লিংকড-লিস্ট) যেগুলো নিরাপদভাবে বর্ণনা করা সম্ভব হলেও Rust-এর বর্তমান বরো-চেকার এখনো ততটা স্মার্ট না যে সেটা প্রমাণ করতে পারে। CPython C-API-র সাথে সরাসরি ইন্টারঅ্যাক্ট করতে গেলে (PyO3-র নিচের লেয়ারে) unsafe লাগে।

কেন এটাই — এটা কি নিরাপত্তা ভেঙে ফেলা?

না — unsafe মানে "সব সেফটি বন্ধ", এটা একটা ভুল ধারণা। এখনো ownership, borrowing (সাধারণ নিয়মে), টাইপ-চেকিং সব চালু থাকে; শুধু ওই পাঁচটা নির্দিষ্ট অপারেশনের জন্য কম্পাইলারের বদলে ডেভেলপারের ম্যানুয়াল প্রমাণের উপর নির্ভর করা হয়। এই ডিজাইনের সুবিধা হলো — যখন একটা বাগ ধরা পড়ে, আপনি জানেন ঠিক কোথায় খুঁজতে হবে: শুধু unsafe ব্লকগুলোতে, পুরো কোডবেসে না। এটাই "unsafe encapsulation" নীতি — নিরাপদ লাইব্রেরি (যেমন Vec নিজেই ভেতরে unsafe ব্যবহার করে) ভেতরে unsafe ব্যবহার করলেও, বাইরে থেকে একদম সেফ API এক্সপোজ করে।

Example 
let x = 5;
let r1 = &x as *const i32;   // raw pointer বানানো — এটা এখনো safe

unsafe {
    println!("value: {}", *r1);   // dereference — এটার জন্যই unsafe লাগল
}

extern "C" {
    fn abs(input: i32) -> i32;   // C ফাংশনের সিগনেচার ঘোষণা
}
unsafe {
    println!("abs(-3) = {}", abs(-3));   // FFI কল — কম্পাইলার C-সাইড সেফটি ভেরিফাই করতে পারে না
}
প্রফেশনাল নোট:
  • নিজের extension কোডে unsafe ব্লক দেখলেই প্রশ্ন করুন — সত্যিই দরকার, নাকি একটা সেফ অল্টারনেটিভ (memoryview, RefCell, ইত্যাদি) আছে। প্রোডাকশন PyO3 এক্সটেনশনে সাধারণত unsafe খুবই কম কোডে সীমাবদ্ধ থাকে (PyO3 নিজেই সেই লেয়ার wrap করে দিয়েছে)।
  • যদি সত্যিই unsafe লিখতে হয়, প্রতিটা unsafe ব্লকের ঠিক উপরে একটা কমেন্টে লিখুন কেন এটা সেফ (কোন invariant বজায় আছে) — এটা GitHub-এর সিরিয়াস Rust প্রজেক্টগুলোর একটা কমন কনভেনশন, রিভিউয়ারদের জন্যও এবং ভবিষ্যতে নিজের জন্যও।
Rust-এর মেমোরি মডেল ও কোর কনসেপ্ট — কম্পাইল-টাইম সেফটি মেকানিজম-লেভেল ব্যাখ্যাসহ।
