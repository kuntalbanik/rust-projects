লেসন ২Intro to Ownership

মূল কথা

Memory হলো কম্পিউটারের একটা হার্ডওয়্যার অংশ যেখানে প্রোগ্রাম চলার সময় সাময়িকভাবে ডেটা রাখে (কম্পিউটার বন্ধ করলে খালি হয়ে যায় — হার্ড ড্রাইভের মতো স্থায়ী না)। Memory সীমিত, তাই প্রোগ্রাম শেষে সেই মেমোরি ফেরত দেওয়া (deallocation) জরুরি। এই সমস্যা তিনভাবে সমাধান করা হয়েছে ইতিহাসে:

তিনটা ভাষা-গোষ্ঠীর মেমোরি-ম্যানেজমেন্ট কৌশলের তুলনা — Rust দুটোর সুবিধাই একসাথে দেয়।
Ownership কী

প্রতিটা ভ্যালুর একজন owner থাকে (সাধারণত একটা variable, কিন্তু ফাংশন প্যারামিটার বা tuple-ও owner হতে পারে)। Owner-ই দায়িত্বে থাকে সেই ভ্যালুর মেমোরি পরিষ্কার করার — ঠিক যেমন বাস্তব জীবনে একটা বাড়ির মালিক সেই বাড়ির দায়িত্বে থাকে। একটা সময়ে একটা ভ্যালুর মালিক একজনই থাকে, তবে সময়ের সাথে মালিক বদলাতে পারে।

প্রফেশনাল নোট: Ownership একটা compiler feature — প্রোগ্রাম রান হওয়ার সময় এর কোনো প্রভাব নেই, রানটাইমে কোনো এক্সট্রা খরচ হয় না। এটা সম্পূর্ণভাবে ডেভেলপারের সুবিধার জন্য — কম্পাইল-টাইমেই মেমোরি-বাগ ধরে ফেলা।

লেসন ৩The Stack and Heap

মূল কথা

Stack কাজ করে "লাঞ্চ ট্রে"-র মতো — ক্যাফেটেরিয়ায় মানুষ যেমন একটার উপর একটা ট্রে রাখে (LIFO — Last In, First Out), stack-ও তেমন। শুধু ফিক্সড-সাইজ ডেটা (int, float, bool, char) এখানে থাকে, কারণ কম্পাইলার আগে থেকেই জানে এদের সাইজ কত। Heap একটা "ওয়্যারহাউস বা পার্কিং লট"-এর মতো — বড়, খোলা জায়গা, যেখানে dynamic (অনিশ্চিত সাইজের, রানটাইমে বদলাতে পারে এমন) ডেটা রাখা হয়। Heap-এ জায়গা খুঁজে দেয় একটা প্রোগ্রাম, যাকে বলে memory allocator — এটা একটা "ঠিকানা" (reference/pointer) ফেরত দেয়, ঠিক যেমন পার্কিং লটে গাড়ি রাখলে একটা স্পট নাম্বার (H25) পাওয়া যায়।

Stack = ফিক্সড-সাইজ, ক্রমানুসারে; Heap = dynamic সাইজ, ঠিকানা দিয়ে অ্যাক্সেস।
গতি কেন আলাদা

Stack-এ যোগ/বিয়োগ সবসময় "উপর থেকে" হয় — তাই দ্রুত। Heap-এ allocator-কে প্রতিবার একটা খালি জায়গা খুঁজে বের করতে হয়, আর পড়ার সময়ও reference অনুসরণ করে ভিন্ন ভিন্ন জায়গায় যেতে হয় — তাই ধীর। Reference নিজে (ঠিকানাটা) কিন্তু ফিক্সড সাইজ বলে stack-এই থাকে, শুধু আসল heap-ডেটাটা বড়/ছোট হতে পারে।

প্রফেশনাল নোট: Ownership মূলত heap ডেটার জন্যই গুরুত্বপূর্ণ — কারণ heap ডেটা বড়, ডুপ্লিকেট হলে বেশি মেমোরি লাগে। Stack ডেটা ছোট, ডুপ্লিকেট করা সস্তা (লেসন ৫ দেখুন)।

লেসন ৪Scope and Ownership

মূল কথা

একটা block মানে { }-এর ভেতরের অংশ, আর scope মানে যে সীমার মধ্যে একটা নাম বৈধ। Variable যে block-এ ডিক্লেয়ার হয়, সেই block শেষ হলেই (curly brace বন্ধ হলেই) সেই variable "scope-এর বাইরে" চলে যায় — আর owner হিসেবে সে তখন তার ভ্যালু পরিষ্কার (drop) করে দেয়।

নেস্টেড ব্লকের ভ্যারিয়েবল বাইরের ব্লক শেষ হওয়ার আগেই নিজের সীমানায় শেষ হয়ে যায়।
Example — LIFO অর্ডারে drop 
fn main() {
    let age = 33;              // প্রথমে push হলো
    let is_handsome = true;    // পরে push হলো
    // ফাংশন শেষে: is_handsome আগে drop (LIFO), তারপর age
}
প্রফেশনাল নোট: "Scope শেষ = drop" — এই নিয়মটাই পুরো ownership সিস্টেমের ভিত্তি। যেকোনো heap-ডেটার (String, Vec ইত্যাদি) জন্য এই একই নিয়ম প্রযোজ্য, শুধু stack entry-এর বদলে heap মেমোরিও পরিষ্কার হয়।

লেসন ৫The Copy Trait

মূল কথা

Trait মানে একটা "প্রতিশ্রুতি" যা একটা টাইপ পূরণ করে। Copy trait মানে: একটা টাইপ পুরোপুরি ডুপ্লিকেট (কপি) করা যায়। Integer, float, bool, char-এর মতো stack-ভিত্তিক টাইপ সবাই Copy trait implement করে — তাই year = time লিখলে দুটো আলাদা, স্বাধীন কপি তৈরি হয়, ownership move হয় না।

Copy trait থাকলে assignment মানেই সম্পূর্ণ নতুন কপি — কোনো ownership move হয় না।
Example 
let time = 2025;
let year = time;
println!("The time is {time}");   // ✅ কাজ করবে
println!("It is the year {year}"); // ✅ কাজ করবে — দুটোই বৈধ
প্রফেশনাল নোট: এটা কিন্তু শুধু ছোট, ফিক্সড-সাইজ stack ডেটার জন্য কাজ করে। লেসন ৮-এ দেখবেন heap ডেটার (String) ক্ষেত্রে এই একই কোড-প্যাটার্ন সম্পূর্ণ ভিন্ন আচরণ করে — কপি না, move হয়।

লেসন ৬The String Type

মূল কথা

Rust-এ দুই ধরনের স্ট্রিং আছে। "pasta"-এর মতো ডাবল-কোটেড টেক্সট আসলে str — compile-time-এই জানা, তাই সরাসরি বাইনারি এক্সিকিউটেবল ফাইলে বসানো থাকে, বদলানো যায় না। String (বড় হাতের S) সম্পূর্ণ ভিন্ন টাইপ — dynamic, mutable, heap-এ থাকে। String::new() দিয়ে খালি String, বা String::from("KitKat") দিয়ে একটা str থেকে heap-এ নতুন String বানানো যায়।

str বাইনারিতে স্থির থাকে; String::from() সেটার ভিত্তিতে heap-এ একটা নতুন, বদলানো-যায়-এমন কপি বানায়।
Example 
let text = String::new();          // খালি String, heap-এ
let candy = String::from("KitKat"); // "KitKat" str থেকে heap String তৈরি
প্রফেশনাল নোট: new এখানে কোনো মেথড না, এটা String namespace-এর ভেতরের একটা plain function — এই জন্যই :: ব্যবহার করে অ্যাক্সেস করতে হয় (. দিয়ে না)।

লেসন ৭The push_str Method

মূল কথা

একটা heap String তৈরি হলে stack-এ তিনটা জিনিস থাকে: reference (heap-এর ঠিকানা), length (এখন কত বাইট ব্যবহৃত), আর capacity (heap-এ মোট কত বাইট রিজার্ভ করা)। push_str() দিয়ে শেষে টেক্সট যোগ (concatenate) করা যায় — যদি capacity-তে জায়গা থাকে, নতুন টেক্সট সেখানেই বসে যায়; জায়গা না থাকলে পুরো ডেটা একটা নতুন, বড় heap স্পটে সরিয়ে নেওয়া হয় আর পুরনো জায়গা ফ্রি হয়ে যায়।

যতক্ষণ capacity আছে, ততক্ষণ push_str() সস্তা; capacity ফুরালে পুরো ডেটা নতুন জায়গায় মুভ হয়।
Example 
let mut name = String::from("Boris");
name.push_str(" Pask");   // concatenation — String হতে হবে mutable
println!("{name}");    // "Boris Pask"
প্রফেশনাল নোট: push_str কখনো একটা str/string-slice ছাড়া অন্য কিছু নেয় না — এটা string literal-এ কাজ করে না কারণ সেটা বাইনারিতে হার্ডকোড করা, mutate করা অসম্ভব (লেসন ৬-এর সাথে সম্পর্ক)।

লেসন ৮Moves and Ownership

মূল কথা

লেসন ৫-এর মতো genius = person লিখলে কী হবে, কিন্তু এবার person একটা heap String — Copy trait নেই। তাই এবার Rust কোনো কপি বানায় না। শুধু stack-এর তিনটা তথ্য (ptr, len, capacity) person থেকে genius-এ কপি হয়, কিন্তু heap-এর আসল টেক্সট একই থাকে। এরপর ownership move হয়ে যায় — genius নতুন owner, আর person সাথে সাথেই invalid হয়ে যায়।

Heap ডেটা কপি হয়নি — শুধু owner বদলে গেছে। person আর ব্যবহারযোগ্য না।
Example — compiler error 
let person = String::from("Boris");
let genius = person;    // move — person invalidated
// println!("{person}");  ❌ error: "borrow of moved value: `person`"
প্রফেশনাল নোট: Rust এভাবেই double-free বাগ প্রতিরোধ করে — যদি person আর genius দুজনেই owner থাকত, দুজনেই scope শেষে একই heap মেমোরি ফ্রি করার চেষ্টা করত, যেটা করাপশন/সিকিউরিটি বাগের কারণ হয়। "শুধু একজন owner" নিয়মে সেই সমস্যাই ঘটতে পারে না।

লেসন ৯The drop Function

মূল কথা

Rust-এর একটা বিল্ট-ইন drop ফাংশন আছে, যেটা heap মেমোরি deallocate করে। Scope শেষ হলে (closing }) Rust নিজে থেকেই প্রতিটা heap-owner variable-এর জন্য এই drop কল করে। চাইলে ম্যানুয়ালিও এটা কল করা যায় — তখন variable-টা সাথে সাথেই invalid হয়ে যায়, scope শেষ হওয়ার অপেক্ষা না করেই।

Example 
let person = String::from("Boris");
drop(person);              // এখনই deallocate, scope শেষের অপেক্ষা নেই
// println!("{person}");  ❌ person আর owner না, ব্যবহার করা যাবে না
// let genius = person;   ❌ move করারও কিছু নেই — person আগেই invalid
প্রফেশনাল নোট: শুধু heap-owner variable-এর জন্যই drop প্রাসঙ্গিক — stack-only ডেটার (int, bool) জন্য এই ফাংশনের কোনো ভূমিকা নেই, কারণ stack এমনিতেই scope শেষে স্বয়ংক্রিয়ভাবে পপ হয়ে যায়।

লেসন ১০The clone Method

মূল কথা

Move এড়িয়ে সত্যিই একটা সম্পূর্ণ, স্বাধীন কপি চাইলে .clone() মেথড কল করতে হয় (এটা Clone trait থেকে আসে)। এটা heap-এ টেক্সট দ্বিতীয়বার কপি করে — তাই দুজন owner (person আর genius) থাকে, প্রত্যেকে নিজের আলাদা heap ডেটার মালিক।

Clone-এ heap-এ ডেটা দুইবার — দুইজন স্বাধীন owner, কিন্তু মেমোরি খরচ দ্বিগুণ।
Example 
let person = String::from("Boris");
let genius = person.clone();   // সম্পূর্ণ নতুন কপি — move হয়নি
println!("{person} {genius}");  // ✅ দুটোই বৈধ — "Boris Boris"
প্রফেশনাল নোট: শুরুতে .clone() নিয়ে দ্বিধা করবেন না — এটা সম্পূর্ণ বৈধ, নিরাপদ সমাধান। পরে অভিজ্ঞতা বাড়লে references (লেসন ১১) দিয়ে অপ্রয়োজনীয় clone কমানো শিখবেন, কিন্তু শুরুতে clone ব্যবহার করা কোনো "খারাপ অভ্যাস" না।

লেসন ১১References and Borrowing

মূল কথা

Clone করলে মেমোরি বেশি লাগে। এর বিকল্প হলো reference — শুধু heap ডেটার ঠিকানা ধার (borrow) করা, মালিকানা না নিয়ে। ঠিক যেমন বাস্তবে গাড়ি ধার করলে আপনি মালিক হয়ে যান না, ব্যবহার করে ফেরত দেন — Rust-এ & (ampersand, "borrow operator") দিয়ে reference বানানো হয়। Rust-এর reference একটা বিশেষ গ্যারান্টি দেয়: এটা কখনো এমন কোনো ঠিকানা দেখাবে না যেখানকার ডেটা আগেই মুছে গেছে ("references must never outlive the referent") — এই কারণেই এটাকে সাধারণ pointer-এর চেয়ে নিরাপদ ধরা হয়।

Reference = ঠিকানা মাত্র, মালিকানা না — মূল owner অক্ষত থাকে।
Example 
let my_heap_value = String::from("Toyota");
let my_heap_reference = &my_heap_value;   // &String — ঠিকানা ধার নেওয়া
// my_heap_value এখনো সম্পূর্ণ বৈধ owner, কিছু হারায়নি
প্রফেশনাল নোট: "Reference" আর "pointer" প্রায় সমার্থক শব্দ হিসেবে ব্যবহৃত হয়, কিন্তু একটা গুরুত্বপূর্ণ পার্থক্য আছে — Rust-এর reference সবসময় বৈধ ডেটার দিকে নির্দেশ করার গ্যারান্টি রাখে (compiler এটা নিশ্চিত করে), সাধারণ pointer অন্য ভাষায় সেই গ্যারান্টি রাখে না — dangling pointer-এর মতো বাগ Rust-এ কম্পাইল-টাইমেই আটকে যায়।

লেসন ১২The Dereference Operator

মূল কথা

* (asterisk) হলো dereference operator — একটা reference-এর ঠিকানা "অনুসরণ" করে আসল ডেটায় পৌঁছানো। শুধু reference-এর সাথেই এটা ব্যবহার করা যায় (সরাসরি ভ্যালুর সাথে না — এরর দেবে)। মজার ব্যাপার: println!-এ reference সরাসরি লিখলেও Rust স্বয়ংক্রিয়ভাবে dereference করে দেয় (Display trait-এর কারণে) — তাই আপনাকে বেশিরভাগ সময় * নিজে লিখতে হয় না।

Example 
let my_stack_value = 2;
let my_integer_reference = &my_stack_value;
println!("{}", *my_integer_reference);   // 2 — ম্যানুয়ালি dereference
println!("{}", my_integer_reference);    // 2 — Rust নিজেই dereference করে দেয়
// *my_stack_value  ❌ error: এটা reference না, dereference করা যায় না
প্রফেশনাল নোট: ম্যানুয়াল * খুবই কম লাগে দৈনন্দিন কোডে (println!, মেথড কল-এ Rust নিজেই সামলে নেয়) — কিন্তু এই মেকানিজম বোঝা জরুরি, কারণ কখনো কখনো (যেমন reference-এর ভ্যালু সরাসরি মডিফাই করতে) এটা explicitly লিখতে হয়।

লেসন ১৩String, &String, str, and &str

মূল কথা — চারটা টাইপ, একনজরে

এই লেসনে আগের সব ধারণা একসাথে জোড়া লাগে। চারটা সম্ভাবনা:

উপরের সারি = heap-ভিত্তিক (রানটাইম), নিচের সারি = বাইনারি-ভিত্তিক (কম্পাইল-টাইম)। ডানের কলাম = রেফারেন্স।
গুরুত্বপূর্ণ প্রমাণ

ভিডিওতে দেখানো হয়েছে — .exe ফাইল একটা Hex Editor দিয়ে খুললে, "Cookies and Cream"-এর মতো string literal সরাসরি বাইনারি ফাইলের ভেতরে খুঁজে পাওয়া যায় (readable টেক্সট আকারে) — প্রমাণ করে যে str সত্যিই কম্পাইল-টাইমেই এক্সিকিউটেবলের ভেতরে বসানো থাকে।

প্রফেশনাল নোট: দৈনন্দিন নিয়ম: টেক্সট বদলাতে/বাড়তে হলে String ব্যবহার করুন; ডুপ্লিকেট এড়াতে reference (&) ব্যবহার করুন; টেক্সট আগে থেকেই জানা এবং স্থির হলে সরাসরি ডাবল-কোট ("...") লিখুন — বাকিটা কম্পাইলার সামলে নেবে।

লেসন ১৪The Copy Trait with References

মূল কথা

একটা reference নিজেও একটা টাইপ, আর references-ও Copy trait implement করে! তাই dessert = ice_cream লিখলে (দুটোই reference) কোনো move হয় না — শুধু reference-টার (ঠিকানাটার) একটা কপি হয়। দুজনেই এখন একই আসল ডেটার (এখানে বাইনারিতে থাকা "Cookies and Cream") দিকে নির্দেশ করে।

দুটো reference, একই আসল টেক্সট — দুটোই সম্পূর্ণ বৈধ, কোনো move নেই।
Example 
let ice_cream = "Cookies and Cream";
let dessert = ice_cream;      // reference কপি হলো, move না
println!("{ice_cream} {dessert}");   // দুটোই বৈধ
প্রফেশনাল নোট: এটাই ব্যাখ্যা করে কেন লেসন ৮-এ person invalid হয়ে গিয়েছিল (String নিজেই ছিল, Copy trait নেই) কিন্তু লেসন ২০-এর প্রজেক্টে string slice (&str) কপি করলে দুটোই বৈধ থেকে যায় — টাইপটা আসলে reference কিনা এটাই আসল পার্থক্য তৈরি করে।

লেসন ১৫Ownership and Function Parameters

মূল কথা

ফাংশনে ভ্যালু পাস করাও ঠিক variable assignment-এর মতোই নিয়ম মানে। Copy trait থাকা টাইপ (int) হলে ফাংশন একটা কপি পায়, মূল variable অক্ষত থাকে। Copy trait না থাকা টাইপ (String) হলে ownership move হয়ে যায় ফাংশন প্যারামিটারে — আর মূল variable ফাংশন কলের পরেই invalid হয়ে যায়।

Copy-টাইপ ফাংশনে গেলে caller-এ কপি থেকে যায়; non-Copy টাইপ ফাংশনে গেলে ownership সেখানেই move হয়ে যায়।
Example 
fn print_my_value(value: String) {
    println!("Your value is {value}");
}   // এখানে value scope শেষে drop হয়ে যায়

let oranges = String::from("oranges");
print_my_value(oranges);
// println!("{oranges}");  ❌ oranges move হয়ে গেছে, আর বৈধ না
প্রফেশনাল নোট: এটা নতুনদের জন্য সবচেয়ে কমন বিভ্রান্তির জায়গা — একটা String ফাংশনে পাঠালে সেটা "হারিয়ে" যায় caller থেকে। এটাই লেসন ১৭-১৮-এ সমস্যা তৈরি করবে, আর References (লেসন ১১-এর ধারণা, পরের সেকশনে আরও গভীরে) এর সমাধান দেবে।

লেসন ১৬Mutable Parameters

মূল কথা

Variable-এর মতোই, ফাংশন প্যারামিটারও ডিফল্টভাবে immutable। burger (mutable variable) থেকে meal (ফাংশন প্যারামিটার)-এ ownership move হলে, meal-এর mutability সম্পূর্ণ নতুন করে ঠিক করতে হয় — burger mutable ছিল কিনা তাতে কিছু যায় আসে না। push_str-এর মতো mutating মেথড কল করতে চাইলে প্যারামিটারের সামনে mut লিখতেই হবে।

Example 
fn add_fries(mut meal: String) {   // mut ছাড়া push_str কম্পাইল-এরর দেবে
    meal.push_str(" and fries");
    println!("{meal}");          // "Burger and fries"
}

let burger = String::from("Burger");   // mut লাগবে না — burger নিজে mutate হয়নি
add_fries(burger);
প্রফেশনাল নোট: Compiler উল্টো দিকেও সতর্ক করে — burger-কে mut লিখলে "variable does not need to be mutable" ওয়ার্নিং আসবে, কারণ burger নিজে কখনো মডিফাই হয়নি, শুধু ownership move হয়েছে। Rust দুই দিকেই — অপ্রয়োজনীয় mutability আর মিসিং mutability — সতর্ক করে।

লেসন ১৭Return Values I

মূল কথা

এখন উল্টো দিক — ফাংশন থেকে একটা owned ভ্যালু return করা। bake_cake() ফাংশনে cake variable একটা String তৈরি করে return করে — ownership bake_cake-এর cake থেকে main-এর cake-এ move হয়ে যায়। Return না করলে ফাংশন শেষে ওই String drop হয়ে যেত।

Return value = ফাংশনের ভেতরের owner থেকে caller-এর নতুন owner-এ ownership পাঠানো।
Example 
fn bake_cake() -> String {
    String::from("Chocolate Mousse")   // সেমিকোলন ছাড়া = implicit return
}

let cake = bake_cake();   // এখানে cake নতুন owner
println!("I now have a cake {cake}");
প্রফেশনাল নোট: Return value না ধরে (bake_cake(); শুধু, কোনো variable-এ assign না করে) কল করলেও প্রোগ্রাম ভাঙে না — কোনো owner না পেলে Rust তখনই সেই ভ্যালু deallocate করে দেয়। মেমোরি-সেফটি সবসময় বজায় থাকে, owner থাকুক বা না থাকুক।

লেসন ১৮Return Values II

মূল কথা — এখানেই সমস্যাটা স্পষ্ট হয়

একটা রেসিপি বানানোর উদাহরণ — add_flour(meal), তারপর add_sugar(meal), ইত্যাদি। প্রতিটা ফাংশনে meal পাস করলে ownership move হয়ে যায়, তাই প্রতিটা ফাংশনকে আবার সেটা return করতে হয়, আর caller-কে আবার সেটা reassign করতে হয় — নাহলে ডেটা হারিয়ে যাবে। একাধিক প্যারামিটার হলে tuple দিয়ে একসাথে সব ফেরত পাঠাতে হবে। এই প্যাটার্ন দ্রুত বিরক্তিকর এবং জটিল হয়ে যায়।

প্রতিটা ফাংশন কল-এ ownership হারানো এড়াতে return করে আবার ধরতে হচ্ছে — বিরক্তিকর প্যাটার্ন।
Example — সমস্যাযুক্ত প্যাটার্ন 
fn add_flour(mut meal: String) -> String {
    meal.push_str("add flour, ");
    meal   // ফেরত না দিলে এই টেক্সট হারিয়ে যাবে
}

let mut current_meal = String::new();
current_meal = add_flour(current_meal);   // বারবার reassign করতে হচ্ছে
প্রফেশনাল নোট: এই সমস্যাটাই পরবর্তী সেকশনের (References) মূল motivation — শুধু &mut meal পাঠালে ownership কখনো move-ই হবে না, তাই এই বারবার return-reassign করার দরকারই পড়বে না। এখানেই কোর্স "References" সেকশনে যাওয়ার প্রস্তুতি নিচ্ছে।

লেসন ২০Project Solution

চ্যালেঞ্জ ১ ও ২ — Copy-টাইপ

is_concert: bool → is_event = is_concert এবং sushi: &str → dinner = sushi — দুটোতেই কোনো move হয় না (bool আর &str দুটোই Copy trait রাখে) — দুজনেই বৈধ থাকে।

চ্যালেঞ্জ ৩ — heap String

একই কোড কিন্তু sushi = String::from("Salmon") হলে — এবার move হয়! dinner নতুন owner, sushi invalid।

চ্যালেঞ্জ ৪ — পুরো চেইন

eat_meal(meal: String) ফাংশন meal.clear() কল করে (একটা heap-mutating মেথড, সব ক্যারেক্টার মুছে দেয়) — তাই meal প্যারামিটার অবশ্যই mut হতে হবে। পুরো ownership-এর যাত্রাটা দেখুন:

"Salmon"-এর মালিকানার সম্পূর্ণ যাত্রা — sushi থেকে শুরু, fish-এ শেষ (কিন্তু ততক্ষণে ফাঁকা, কারণ clear() কল হয়েছে)।
Example 
fn eat_meal(mut meal: String) -> String {
    meal.clear();   // সব ক্যারেক্টার মুছে দেয় — mut লাগবে
    meal
}

let sushi = String::from("Salmon");
let dinner = sushi;              // move ১
let fish = eat_meal(dinner);     // move ২ + move ৩ (return)
println!("{fish}");              // "" — খালি, clear() হয়ে গেছে
প্রফেশনাল নোট: কোনো ভ্যালু Copy trait রাখে কিনা সন্দেহ হলে সহজ ট্রিক: assignment-এর পর দুটো variable-ই ব্যবহার করার চেষ্টা করুন — দুটোই বৈধ থাকলে Copy হয়েছে, একটা invalid হলে move হয়েছে।

Fn Parametersফাংশনে ভ্যালু পাঠানো = assignment-এর মতোই কপি বা move নিয়ম মানে
Return ValuesReturn করা মানে ownership ফাংশনের ভেতর থেকে caller-এ ফেরত পাঠানো
যেকোনো assignment/function-call দেখলে এই একই তিনটা প্রশ্ন দিয়ে বিচার করুন।
প্রফেশনাল নোট: লেসন ১৮-এর "return-reassign" সমস্যাটাই পরের সেকশনের (References) আসল কারণ — প্রতিটা ফাংশন কলে ownership হারানো এড়াতে references ব্যবহার করাই বাস্তব প্রোডাকশন কোডের স্ট্যান্ডার্ড প্র্যাকটিস। এই সেকশনের বেসিক ভালোভাবে বসে গেলে references সেকশনটা অনেক সহজ লাগবে।
Rust Ownership কোর্স (সেকশন ০৬) — আপলোড করা ভিডিও ট্রান্সক্রিপ্ট অনুযায়ী, সহজ বাংলায়, ছবিসহ।
