Trait Objects (dyn Trait) — আরেক ধরনের Fat Pointer

কী ও কেন

0x09 (Part 1)-এ দেখেছিলেন slice &[T] একটা fat pointer — (ptr, len)। &dyn Trait বা Box<dyn Trait>ও একটা fat pointer, কিন্তু ভিন্ন দুটো জিনিস বহন করে: (১) data pointer — আসল ভ্যালুটা heap-এ কোথায় আছে, (২) vtable pointer — একটা "ভার্চুয়াল টেবিল"-এর ঠিকানা, যেটা এই নির্দিষ্ট টাইপের জন্য trait-এর প্রতিটা মেথডের প্রকৃত ফাংশন-অ্যাড্রেস লিস্ট করে রাখে। vtable কম্পাইল-টাইমেই তৈরি হয়ে প্রোগ্রামের static/read-only মেমোরিতে বসে থাকে — প্রতিটা (টাইপ, trait) জোড়ার জন্য একটাই vtable, রানটাইমে তৈরি হয় না।

যখন আপনি obj.method() কল করেন একটা dyn Trait-এর উপর, রানটাইমে vtable থেকে সঠিক ফাংশন-পয়েন্টার তুলে এনে কল করা হয় — একে বলে dynamic dispatch। এটা 0x08 (আগের ডকুমেন্টের Traits & Generics টপিক)-এ উল্লেখ করা static dispatch-এর ঠিক বিপরীত, যেখানে কম্পাইলার কম্পাইল-টাইমেই জানে কোন ফাংশন কল হবে।

Purpose / কোথায় ব্যবহার

যখন একটা কালেকশনে (যেমন Vec<Box<dyn Shape>>) বিভিন্ন কনক্রিট টাইপ (Circle, Rectangle, Triangle...) একসাথে রাখতে হবে, যাদের কম্পাইল-টাইমে সংখ্যা বা ধরন আগে থেকে জানা নেই — generics দিয়ে এটা সম্ভব না (generics একটা নির্দিষ্ট কনক্রিট টাইপে "মনোমরফাইজড" হয়), তাই dynamic dispatch দরকার।

কেন এটাই — খরচ কী

Static dispatch (generics)-এর তুলনায় dynamic dispatch-এ দুটো এক্সট্রা খরচ আছে: (১) প্রতিটা মেথড কলে vtable থেকে ফাংশন-পয়েন্টার লুকআপ (এক ধাপ indirection, CPU-র branch predictor-কেও কিছুটা কনফিউজ করতে পারে), (২) প্রতিটা কনক্রিট টাইপের জন্য আলাদা কোড জেনারেট না হওয়ায় (একটাই শেয়ার্ড কোড-পাথ) কম্পাইলার inlining-এর মতো অপ্টিমাইজেশন করতে পারে না। এই খরচের বিনিময়ে যা পাওয়া যায় তা হলো নমনীয়তা — heterogeneous কালেকশন এবং ছোট বাইনারি সাইজ (মনোমরফাইজেশনের "code bloat" এড়ানো)।

dyn Trait = দুই পয়েন্টারের fat pointer — একটা ডেটার দিকে, একটা vtable-এর দিকে যা প্রতিটা মেথডের প্রকৃত অ্যাড্রেস জানে।
Example 
trait Shape { fn area(&self) -> f64; }

struct Circle { r: f64 }
impl Shape for Circle { fn area(&self) -> f64 { std::f64::consts::PI * self.r * self.r } }

struct Square { side: f64 }
impl Shape for Square { fn area(&self) -> f64 { self.side * self.side } }

let shapes: Vecdyn Shape>> = vec![
    Box::new(Circle { r: 2.0 }),
    Box::new(Square { side: 3.0 }),
];   // দুটো ভিন্ন কনক্রিট টাইপ, একই Vec-এ — শুধু dyn Trait দিয়েই সম্ভব
for s in &shapes { println!("{}", s.area()); }   // প্রতিটা কলে vtable লুকআপ
প্রফেশনাল নোট: PyO3-তে যখন আপনি Python থেকে বিভিন্ন ধরনের callback/handler নেন, প্রায়ই ভেতরে Box<dyn Fn(...)>-এর মতো প্যাটার্ন ব্যবহার হয় — কারণ Python-সাইড থেকে কোন নির্দিষ্ট ফাংশন আসবে তা কম্পাইল-টাইমে জানা সম্ভব না, dynamic dispatch ছাড়া উপায় নেই।

Rc<T> / Arc<T> — ভেতরের গঠন

কী ও কেন

0x04 (Part 1)-এ শিখেছেন প্রতিটা ভ্যালুর ঠিক একজন owner থাকে। কিন্তু কখনো কখনো সত্যিই একাধিক জায়গা থেকে একই ডেটার "যৌথ মালিকানা" দরকার (যেমন একটা গ্রাফ ডেটা-স্ট্রাকচার, যেখানে একটা নোড একাধিক প্যারেন্টের থেকে রেফারেন্সড)। Rc<T> (Reference Counted) এটা সম্ভব করে একটা রানটাইম রেফারেন্স-কাউন্টার দিয়ে — অনেকটা 0x02 (আগের ডকুমেন্টের 3.2)-এ দেখা CPython-এর refcounting-এর মতোই একটা মেকানিজম, কিন্তু এখানে এটা library-level, ভাষার বিল্ট-ইন ফিচার না।

যখন Rc::new(value) কল করেন, heap-এ একটা একক ব্লক (RcBox) অ্যালোকেট হয় যেটাতে তিনটা জিনিস একসাথে থাকে: strong_count, weak_count, আর আসল ভ্যালু T। .clone() কল করলে কোনো নতুন heap অ্যালোকেশন হয় না — শুধু একটা নতুন stack-এ Rc হ্যান্ডেল তৈরি হয়, সবাই একই RcBox-কে পয়েন্ট করে, আর strong_count ১ বেড়ে যায়। যখন একটা Rc handle drop হয়, count ১ কমে; count শূন্যে নামলেই heap ডেটা আসলে ফ্রি হয়।

Purpose / কোথায় ব্যবহার / কেন এটাই — Rc vs Arc

Rc<T> সিঙ্গেল-থ্রেডেড কনটেক্সটে ব্যবহার করুন — এর কাউন্টার আপডেট plain, non-atomic ইন্টিজার অপারেশন, তাই দ্রুত কিন্তু থ্রেড-সেফ না (তাই এটা Send/Sync না, 0x0B আগের ডকুমেন্টের Fearless Concurrency)। Arc<T> (Atomic Rc) হুবহু একই আইডিয়া, কিন্তু কাউন্টার আপডেট atomic CPU instruction দিয়ে — থ্রেড-সেফ, তাই মাল্টি-থ্রেডেড শেয়ারিংয়ে (যেমন Arc<Mutex<T>>) ব্যবহার হয়। Atomic অপারেশন plain integer অপারেশনের চেয়ে সামান্য ধীর — তাই সিঙ্গেল-থ্রেডেড কোডে Rc-ই যথেষ্ট এবং প্রেফারড।

Rc/Arc — একটাই heap অ্যালোকেশনে ভ্যালু + কাউন্টার একসাথে, একাধিক stack handle সেটা শেয়ার করে।
Example 
use std::rc::Rc;

let a = Rc::new(String::from("shared"));
println!("count = {}", Rc::strong_count(&a));   // 1
let b = Rc::clone(&a);                          // heap allocation হয়নি, শুধু count++
println!("count = {}", Rc::strong_count(&a));   // 2
drop(b);
println!("count = {}", Rc::strong_count(&a));   // 1
প্রফেশনাল নোট:
  • Rc<T> ডিফল্টভাবে immutable ডেটা শেয়ার করে — mutation চাইলে সাধারণত Rc<RefCell<T>> (0x0C দেখুন) প্যাটার্ন লাগে।
  • দুটো Rc যদি একে অপরকে পয়েন্ট করে (cycle), strong_count কখনো শূন্যে নামবে না — মেমোরি লিক (0x10 দেখুন)। এড়াতে Weak<T> ব্যবহার করুন, যেটা শুধু weak_count বাড়ায়, strong_count না।

RefCell<T> — Interior Mutability & Runtime Borrow Check

কী ও কেন

0x03 (আগের ডকুমেন্টের Aliasing Rules)-এ শেখা "একসাথে হয় একাধিক &T, অথবা একটা &mut T" — এই নিয়ম সাধারণত কম্পাইল-টাইমে চেক হয়। কিন্তু কখনো কখনো এমন প্যাটার্ন লেখার দরকার হয় যেখানে কম্পাইলার প্রমাণ করতে পারে না নিয়মটা মানা হচ্ছে কিনা (যদিও রানটাইমে আসলে ঠিকই থাকে) — যেমন একটা struct-এর একটা ফিল্ড শুধু মাঝেমধ্যে মডিফাই করা দরকার, একটা immutable রেফারেন্সের মধ্য দিয়েও।

RefCell<T> এই একই নিয়ম প্রয়োগ করে, কিন্তু কম্পাইল-টাইমের বদলে রানটাইমে। এটার heap বা stack representation-এ (যেখানেই থাকুক) আসল ভ্যালু T-এর পাশে একটা লুকানো কাউন্টার (borrow_flag: Cell<isize>) থাকে — শূন্য মানে কোনো borrow নেই, পজিটিভ সংখ্যা N মানে N-টা immutable borrow সক্রিয়, একটা বিশেষ নেগেটিভ ভ্যালু মানে একটা mutable borrow সক্রিয়। .borrow()/.borrow_mut() কল করলে এই ফ্ল্যাগ চেক হয় — নিয়ম ভাঙলে কম্পাইল-এরর না, বরং রানটাইম panic।

Purpose / কেন এটাই — vs কম্পাইল-টাইম চেক

ট্রেড-অফ স্পষ্ট: RefCell দিয়ে এমন প্যাটার্ন সম্ভব যা pure কম্পাইল-টাইম borrow-checking দিয়ে লেখা যেত না (কম্পাইলার কখনো কখনো একটা প্যাটার্নকে ভুল করে "সন্দেহজনক" মনে করে বাতিল করে দেয়, যদিও লজিক্যালি সঠিক), কিন্তু নিয়ম-লঙ্ঘনের বাগ এখন রানটাইমে ধরা পড়বে (একটা panic হিসেবে), কম্পাইল-টাইমে না। তাই RefCell "নিয়ম বাতিল করে" না — শুধু নিয়ম চেক করার সময়টা পিছিয়ে দেয়।

borrow_flag ভ্যালুর সাথেই থাকে — প্রতিটা borrow/borrow_mut কল এই ফ্ল্যাগ চেক করে, ঠিক যেমন কম্পাইলার কম্পাইল-টাইমে করত।
Example 
use std::cell::RefCell;

let data = RefCell::new(5);
let r1 = data.borrow();          // flag: 0 → 1
println!("{}", *r1);
let r2 = data.borrow_mut();      // ❌ রানটাইম panic: already borrowed: BorrowMutError
প্রফেশনাল নোট: Rc<RefCell<T>> একসাথে খুবই কমন কম্বিনেশন — Rc একাধিক owner দেয় (0x0B), RefCell সেই শেয়ার্ড ডেটা মডিফাই করার সুযোগ দেয়। মাল্টি-থ্রেডেড কনটেক্সটে এর সমতুল্য হলো Arc<Mutex<T>> — Mutex-ও একই আইডিয়া, কিন্তু ব্লক করে অপেক্ষা করে (panic করার বদলে), আর atomic/OS-level locking ব্যবহার করে থ্রেড-সেফটির জন্য।

Closures — মেমোরিতে আসলে কী

কী ও কেন

একটা closure দেখতে একটা ফাংশনের মতো লাগলেও, কম্পাইলার এটাকে ভেতরে ভেতরে একটা anonymous struct-এ রূপান্তর করে — যে ভ্যারিয়েবলগুলো closure-টা "capture" করে (নিজের বডির বাইরের স্কোপ থেকে ব্যবহার করে), সেগুলোই সেই struct-এর ফিল্ড হয়ে যায়। তারপর কম্পাইলার সেই struct-এর জন্য Fn/FnMut/FnOnce ট্রেইট (0x08, আগের ডকুমেন্ট) implement করে দেয়, যার মূল মেথড closure-এর বডি এক্সিকিউট করে। "Closure লেখা" মানে আসলে একটা নামহীন struct + trait impl জেনারেট করা।

Purpose / কোথায় ব্যবহার

Capture তিন রকম হতে পারে — by reference (&T, ডিফল্ট, যদি শুধু পড়া হয়), by mutable reference (&mut T, মডিফাই করলে), অথবা by value (move কীওয়ার্ড দিয়ে জোর করে মালিকানা নিয়ে নেওয়া — থ্রেডে পাঠানো closure-এর জন্য প্রায়ই বাধ্যতামূলক, কারণ থ্রেড কতক্ষণ বাঁচবে caller জানে না)।

Closure = capture করা ভ্যারিয়েবল যার ফিল্ড, আর body যার মেথড — এমন একটা কম্পাইলার-জেনারেটেড struct।
Example 
let y = 10;
let add_y = move |x: i32| x + y;   // y-এর মালিকানা নিয়ে নিল (Copy টাইপ, তাই কপি হলো)
println!("{}", add_y(5));   // 15

let data = vec![1, 2, 3];
let print_data = move || println!("{:?}", data);   // data-এর মালিকানা closure-এ move হলো
std::thread::spawn(print_data).join().unwrap();   // থ্রেডে নিরাপদে পাঠানো গেল, কারণ ownership আছে
প্রফেশনাল নোট: thread::spawn-এ পাঠানো যেকোনো closure-এ প্রায় সবসময় move লাগবে — নাহলে কম্পাইলার নিশ্চিত করতে পারবে না closure-টার capture করা রেফারেন্স থ্রেডের পুরো জীবনকাল জুড়ে বৈধ থাকবে (lifetime, 0x04 আগের ডকুমেন্ট)। এটাই PyO3-র py.allow_threads() বা rayon-এর .par_iter()-এ পাঠানো closure-গুলোতেও প্রযোজ্য নিয়ম।
0x0E

Zero-Sized Types (ZST) — যারা মেমোরিতে ০ বাইট নেয়

কী ও কেন

কিছু টাইপে কোনো প্রকৃত ডেটা থাকে না — শুধু একটা "টাইপ-লেভেল তথ্য" বহন করে। যেমন একটা unit struct (struct Marker;), অথবা () (unit type), অথবা PhantomData<T>। এদের std::mem::size_of ঠিক ০ — মেমোরিতে এরা আক্ষরিক অর্থেই কোনো জায়গা নেয় না। কম্পাইলার এমনভাবে কোড জেনারেট করে যে এই টাইপের কোনো ইনস্ট্যান্স তৈরি/সরানো আসলে রানটাইমে কোনো CPU instruction-ই তৈরি করে না (সম্পূর্ণ "free")।

Purpose / কোথায় ব্যবহার

Type-level marker হিসেবে — যেমন একটা HashSet<T> ভেতরে আসলে একটা HashMap<T, ()> (key আছে, ভ্যালু হিসেবে অর্থহীন unit — এভাবে HashMap-এর কোড পুনর্ব্যবহার হয়, কোনো এক্সট্রা মেমোরি খরচ ছাড়াই)। PhantomData ব্যবহার হয় generics-এ যখন একটা টাইপ প্যারামিটার T struct-এ "ব্যবহৃত" বলে দেখাতে হবে (variance/drop-check-এর জন্য) কিন্তু বাস্তবে কোনো T ভ্যালু স্টোর করা হচ্ছে না — যেমন raw pointer wrapper টাইপে।

ZST দিয়ে ভরা একটা Vec-এরও heap-এ কোনো প্রকৃত বাফার লাগে না — এটাই "zero-cost" ধারণার একটা চরম উদাহরণ।
Example 
use std::mem::size_of;

struct Marker;   // unit struct — কোনো ফিল্ড নেই
println!("{}", size_of::());   // 0
println!("{}", size_of::<()>());       // 0
println!("{}", size_of::<[Marker; 1000]>());   // এখনো 0!
প্রফেশনাল নোট: ZST একটা "ফ্রি" টাইপ-সেফটি টুল — যেমন একটা enum ফাংশনে বিভিন্ন "মোড" মার্ক করতে ZST struct ব্যবহার করলে, রানটাইমে কোনো বাড়তি মেমোরি না খরচ করেই কম্পাইল-টাইম গ্যারান্টি পাওয়া যায় (এই প্যাটার্নকে "typestate pattern" বলা হয়) — কিছু GitHub প্রজেক্টে state machine মডেল করতে এভাবে ব্যবহার হতে দেখবেন।
0x0F

Drop Order — ঠিক কোন অর্ডারে Cleanup হয়

কী ও কেন

0x01 (Part 1)-এ দেখেছেন owner স্কোপ ছাড়লেই drop() স্বয়ংক্রিয়ভাবে ট্রিগার হয়। কিন্তু একাধিক ভ্যালু জড়িত থাকলে অর্ডারটা কী? দুটো নিয়ম: (১) একটা স্কোপে ডিক্লেয়ার করা স্ট্যাক ভ্যারিয়েবলগুলো drop হয় উল্টো অর্ডারে (যেটা সবার শেষে তৈরি হয়েছিল, সেটা সবার আগে drop হয় — LIFO, ঠিক stack-এরই মতো)। (২) একটা struct-এর ফিল্ডগুলো drop হয় ডিক্লেয়ারেশন অর্ডারে (উপর থেকে নিচে, যেভাবে struct-এ লেখা হয়েছে)।

Purpose / কেন এটা গুরুত্বপূর্ণ

যদি একটা রিসোর্স আরেকটার উপর নির্ভরশীল (যেমন একটা ডাটাবেস কানেকশন একটা লগ-ফাইল হ্যান্ডেলের উপর নির্ভর করে ক্লোজিং মেসেজ লিখতে), তাহলে drop অর্ডার ভুল হলে বাগ হতে পারে — dependent রিসোর্স আগে drop হয়ে যাওয়া উচিত, dependency পরে। Rust-এর predictable, ডকুমেন্টেড drop-অর্ডার এই ধরনের রিসোর্স-ম্যানেজমেন্ট কোড লেখা সম্ভব করে।

Stack ভ্যারিয়েবল: LIFO (উল্টো অর্ডার)। Struct ফিল্ড: ডিক্লেয়ারেশন অর্ডার (সোজা)।
Example 
struct Loud(&'static str);
impl Drop for Loud {
    fn drop(&mut self) { println!("dropping {}", self.0); }
}

fn main() {
    let _a = Loud("a");
    let _b = Loud("b");
    let _c = Loud("c");
}
// আউটপুট: "dropping c", "dropping b", "dropping a" — সবসময় উল্টো অর্ডারে
প্রফেশনাল নোট: কোনো ভ্যালু নির্দিষ্ট অর্ডারে ম্যানুয়ালি আগেভাগে drop করতে চাইলে std::mem::drop(value) কল করুন — এটা ownership নিয়ে সাথে সাথেই drop ট্রিগার করে, স্কোপ শেষ হওয়া পর্যন্ত অপেক্ষা করতে হয় না।
0x10

Safe Rust-এও মেমোরি লিক সম্ভব

কী ও কেন — একটা ভুল ধারণা ভাঙা

"Rust মেমোরি-সেফ" মানে use-after-free, double-free, data race — এই নির্দিষ্ট ক্লাসের বাগ কম্পাইল-টাইমে আটকানো, এটা "কখনো মেমোরি লিক হবে না" এই গ্যারান্টি না। আসলে Rust-এর নিজের ডকুমেন্টেশনেও স্পষ্ট বলা আছে — মেমোরি লিক নিরাপদ (memory-safe), শুধু অপচয়। তিনটা কমন উপায়ে নিরাপদ (safe) Rust কোডেও লিক ঘটতে পারে।

১. Rc/Arc সাইকেল

0x0B-এ দেখা গঠন মনে করুন — strong_count শূন্যে না নামা পর্যন্ত heap ডেটা ফ্রি হয় না। যদি A একটা Rc দিয়ে B-কে পয়েন্ট করে, আর B একটা Rc দিয়ে আবার A-কে পয়েন্ট করে, তাহলে বাইরের সব রেফারেন্স হারিয়ে গেলেও A আর B একে অপরের strong_count ধরে রাখবে — কখনো শূন্যে নামবে না, কখনো ফ্রি হবে না।

২. mem::forget() এবং Box::leak()

std::mem::forget(value) ইচ্ছাকৃতভাবে একটা ভ্যালুর Drop স্কিপ করে দেয় (ownership নিয়ে নেয়, কিন্তু destructor কল করে না) — এটা সেফ ফাংশন, কারণ এটা কোনো ইতিমধ্যে-ফ্রি-হওয়া মেমোরি অ্যাক্সেস করায় না, শুধু ফ্রি করাটাই এড়িয়ে যায়। Box::leak() একইভাবে একটা Box-কে ইচ্ছাকৃতভাবে "চিরকালীন" ('static) রেফারেন্সে বদলে দেয়, যার মানে সেই মেমোরি প্রোগ্রাম শেষ না হওয়া পর্যন্ত কখনো ফ্রি হবে না।

দুটো Rc একে অপরকে ধরে রাখলে refcount কখনো ০ হয় না — সাইলেন্ট মেমোরি লিক।
Example 
use std::rc::Rc;
use std::cell::RefCell;

struct Node { next: RefCell<Option>> }

let a = Rc::new(Node { next: RefCell::new(None) });
let b = Rc::new(Node { next: RefCell::new(Some(Rc::clone(&a))) });
*a.next.borrow_mut() = Some(Rc::clone(&b));   // এখন a→b→a একটা সাইকেল — কখনো drop হবে না
প্রফেশনাল নোট:
  • যেকোনো parent-child বা tree-স্টাইল ডেটা-স্ট্রাকচারে child-থেকে-parent-এর দিকের রেফারেন্স Weak<T> রাখুন, parent-থেকে-child-এর দিকটা Rc<T> — এটাই সাইকেল এড়ানোর স্ট্যান্ডার্ড কনভেনশন।
  • Leak হওয়া মানে ক্র্যাশ বা আনডিফাইনড বিহেভিয়ার না — শুধু মেমোরি ব্যবহার ক্রমাগত বাড়তে থাকা (একটা long-running সার্ভার প্রসেসে এটা আসলে একটা গুরুতর প্রোডাকশন বাগ, তাই কম্পাইল-টাইমে ধরা না পড়লেও এটাকে হালকাভাবে নেওয়া ঠিক না)।
